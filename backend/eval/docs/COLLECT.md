# 사진 모으기 체크리스트

중고나라에서 평가용 사진을 모을 때 이 순서대로 한다. 숫자를 믿을 수 있으려면
**좋은 결과가 나올 것 같은 사진을 고르지 않는 것**이 제일 중요하다 (고르면 통과율이 부푼다).

**게시글 단위로 모은다** (10-04). 실제 사용자는 사진을 여러 장 올리고, 그 안에 한 물건의 여러 각도 · 택 · 하자 클로즈업 ·
보증서 · 여러 물건이 섞인다 — 그 섞임이 우리가 알아야 할 분포다. 게시글의 첫 사진은 지금처럼 한 장 평가에 쓰고,
나머지는 여러 장 평가(묶기 · 사진 역할)에 쓴다. 여러 장 라벨은 분석 설계가 정해지면 단다 (`study/2026-10-04-analysis-two-stage.md` §5).

설계 근거: `study/2026-09-29-test-cleanup.md` §4 — test 100장이면 통과율 95% 구간이 ±8%p,
50장이면 ±11%p, 경로별로 나누면 그 두 배 가까이 벌어진다.

## 1. 규칙 (모으기 전에 읽기)

1. **검색어는 아래 표에서만** 고른다. 표에 없는 걸 찾고 싶으면 먼저 표에 적고 쓴다
2. 검색 결과를 **최신순**으로 보고, 조건에 맞는 **첫 게시글의 사진을 전부** (게시글 순서대로, 앞에서 최대 10장) 가져온다
   - 게시글을 고르는 기준은 **첫 사진**이다. 첫 사진이 제외 기준에 걸리면 그 게시글은 건너뛰고 다음 게시글
     (같은 글의 두 번째 사진을 첫 사진으로 바꾸지 않는다)
   - 두 번째 사진부터는 **제외 기준을 보지 않고 전부** — 가격표 · 스크린샷 · 같은 사진 두 번이 섞여 있어도 그게 실제 업로드다
     (같은 사진은 `dup_of` 로 남는다). 10장이 넘으면 다 넣어도 된다 — `add` 가 앞 10장만 옮기고 원래 장수를 남긴다
   - 그래서 여러 장 세트는 "첫 사진이 판매자 직접 촬영인 게시글"로 좁혀진다 (표지가 착용샷 · 공식 이미지인 글은 빠진다). 알고 고른 범위다
   - 두 번째 사진부터는 라벨이 없어 `private` 를 못 단다 — 채팅 캡처 · 연락처 · 영수증이 섞일 수 있으니 이 사진들은 결과 페이지에 올리지 않는다
   - "이건 결과가 안 좋겠다" · "이건 잘 되겠다"는 이유로 건너뛰지 않는다
3. 한 검색어에서 **최대 3개 게시글** — 한 종류 물건이 몰리지 않게. 채우면 다음 검색어로
4. 층 목표(게시글 수)를 다 채우면 그 층은 멈춘다 (`python eval/intake.py status` 로 확인 — 넘기면 `add` 가 거부한다)
5. 같은 판매자 게시글은 하나만

**제외** (첫 사진이 이러면 그 게시글을 건너뛴다)

- 사람이 주인공 (착용샷, 얼굴이 크게 나옴)
- 스크린샷 · 캡처 · 쇼핑몰 공식 이미지 (판매자가 직접 찍은 사진이 아님)
- 여러 장을 한 장으로 합친 콜라주
- 물건이 너무 작거나 안 보임 (물건이 사진의 1/10 도 안 됨)
- 가격표 · 글만 있는 이미지

**제외하지 않는 것** — 흔들림 · 어두움 · 지저분한 배경 · 워터마크 · 비스듬한 각도.
이게 실제 사용자가 올리는 사진이다.

## 2. 층별 목표와 검색어

`코드`는 게시글 폴더 이름 앞에 붙인다. 층은 **첫 사진을 보고** 정한다 (검색어가 "하자"여도 사진이 멀쩡하면 none).
목표 수는 게시글 수다 (게시글마다 첫 사진이 한 장 평가 세트에 들어간다).

| 코드 | 층 | test | dev | 어떤 사진 | 검색어 |
|---|---|---|---|---|---|
| `none` | 물건 · 하자 없음 | 25 | 5 | 새것 같은 물건 | 무선이어폰, 운동화, 백팩, 텀블러, 키보드, 스탠드 조명, 전기포트, 게임패드, 선글라스, 손목시계 |
| `wear` | 물건 · 하자 · 흔적 있음 | 35 | 8 | 얼룩 하나부터 녹 · 도장 벗겨짐 · 찢김까지 — 작든 크든 흔적이 보이면 | 두 묶음을 **번갈아**: ① none 검색어 + "사용감" · "생활기스" · "스크래치" ② 하자 있음, 고장, 부품용, 녹, 도색 벗겨짐, 가죽 까짐 |
| `dense` | 물건 · 잔글씨 많음 | 10 | 3 | 라벨 · 성분표 · 눈금 · 스펙 표가 크게 보임 | 화장품, 영양제, 공구, 전자제품 박스, 향수, 계측기 |
| `doc` | 글자가 곧 물건 | 15 | 4 | 표지 · 제목이 물건의 전부 | 전공책, 소설, 문제집, 만화책, CD 앨범, LP, 악보 |
| `inside` | 물건 일부 · 내부 | 8 | 2 | 엔진룸 · 뜯은 기기 · 한 곳 클로즈업 | 엔진룸, 메인보드, 그래픽카드, 노트북 분해, 시계 무브먼트, 자동차 실내 |
| `edge` | 판단이 애매 | 7 | 3 | 무엇을 지켜야 할지 사람도 헷갈리는 것 — 의도된 손상인지 하자인지 · 글자·그림이 곧 물건인지 · 팔 물건과 소품·구성품이 섞였는지 | 데미지 청바지, 디스트레스 청바지, 포토카드, 엽서, 앨범 풀구성, 보드게임 |
| | **합계** | **100** | **25** | | |

- `wear` 는 10-04 에 light · heavy 를 합쳤다. 분석이 하자 수준(작다 · 크다) 대신 "다시 그리기 어려운 흔적이 넓게 있나"를
  보기로 해서 (study 10-04 §4), 둘로 나눠 모을 이유가 없다. 흔적이 넓은지는 층이 아니라 라벨로 단다 —
  기준선까지는 그 라벨이 `wear_level` (light · heavy) 이다
- wear 검색어는 ① ② 를 하나씩 번갈아 쓴다. ① 만 순서대로 쓰면 30개 조합으로 목표가 먼저 차서 ② (큰 하자)가 하나도 안 들어온다 —
  앱은 아직 큰 하자면 생성하지 않는 경로(`wear_heavy`)가 있어 그 표본이 필요하다
- `edge` 층은 **판단이 애매한 것만**이다 (10-04 좁힘). 투명 · 반사 · 가려짐 · 잘림 · 워터마크처럼
  "판단은 분명한데 오리기 · 생성이 어려운 것"은 층이 아니라 **edge 태그**(아래 §2-1)로 단다 —
  유리컵 새것은 `none` 층 + `transparent` 태그
- edge 층 사진에는 judge 태그(`intended_damage` · `text_is_item` · `prop`)가 하나 이상 붙는다. 거꾸로 judge 태그가
  붙었다고 edge 층은 아니다 — 옷걸이에 걸린 옷(`prop`)은 무엇을 팔지 분명하니 none 층.
  `ambiguous=y` 는 따로 — 라벨 다는 사람이 정답을 확신 못 할 때 (edge 층이어도 정답이 분명하면 빈칸)
- dev 는 조정용 — 실패를 보고 프롬프트를 고쳐도 된다. test 는 동결 — 결과만 본다
- test/dev 는 정리 스크립트가 층별로 나눈다 (직접 고르지 않는다)
- test/dev 는 층마다 자리를 미리 섞어 두고 들어온 순서대로 채운다 — 조금씩 `add` 해도 dev 가 한 검색어에 몰리지 않는다
- 한 번 정한 split 은 `splits.jsonl` 에 남는다. `status` 가 바뀐 게 있으면 알려 준다
- 기존 8장(`phone_img/` 에서 온 사진)은 규칙 없이 고른 사진이라 **층 목표에 세지 않고** dev 에 따로 둔다
- 규칙 전에 모았거나 결과를 먼저 볼 사진(파일럿)은 `add --pilot` — 역시 층 목표 밖, 전부 dev

## 2-1. edge 태그 — 사진 성격 (여러 개, 어느 층이든)

라벨 달 때 해당하는 걸 **전부** `edge_tags` 칸에 `|` 로 이어 단다 (없으면 빈칸). 층은 "모을 때의 의도" 하나,
태그는 "사진이 가진 어려움" 여러 개 — 손에 든 신발은 `none` 층 + `hand_held|occluded`.
값은 `intake.py` 의 `EDGE_TAGS` 와 같다. 새 태그가 필요하면 이 표와 `EDGE_TAGS` 에 먼저 넣는다.

| 묶음 | 태그 | 다는 경우 |
|---|---|---|
| judge 판단이 애매 | `intended_damage` | 디스트레스 · 워싱 · 빈티지 가공 — 하자처럼 보이지만 디자인 |
| | `text_is_item` | 글자 · 그림이 물건의 전부인지 애매 (포토카드 · 포스터 · 엽서) |
| | `prop` | 팔 물건 말고 소품 · 구성품 · 상자가 같이 찍힘 (옷걸이 · 박스 · 구성품) |
| cut 오리기 · 검출 | `transparent` | 투명 · 반투명 (유리 · 아크릴 · 투명 케이스) |
| | `glossy_material` | 광택 · 반사가 큼 (크롬 · 에나멜 · 광택 나일론) |
| | `occluded` | 물건 일부가 다른 것에 가려짐 |
| | `hand_held` | 손에 들고 찍음 |
| | `cut_off` | 팔 물건이 사진 밖으로 잘림 (앱은 배경 제거만 한다) |
| gen 생성에서 망가지기 쉬움 | `watermark` | 물건 위에 워터마크 · 자막 · 판매자 글씨 |
| | `small_text` | 아주 작은 글자가 물건 일부 (다이얼 · 성분표 · 케어 라벨) |
| | `pattern` | 그림 · 프린트 · 체크 같은 반복 무늬 |
| | `embroidery` | 자수 · 패치 |
| | `tag` | 택 · 라벨이 붙어 있음 |
| | `subtle_wear` | 눈에 잘 안 띄는 작은 하자 (앞코 얼룩 · 다이얼 얼룩) |
| | `packaging` | 비닐 · 케이스 포장 째 찍음 (미개봉 · 새상품) |
| privacy | `private` | 번호판 · 얼굴 · 전화번호 — 결과 페이지에 올릴 때 가린다 |

- 여러 개(같은 물건 2개 이상)는 태그가 아니라 `item_count` 칸에 개수로 (앱은 배경 제거만 한다)

### 최소 수와 보충

- 처음부터 태그를 노리고 고르지 않는다 (§1 규칙 그대로). 태그는 모은 뒤 라벨 때 단다
- **최소 5장은 검색어로 노릴 수 있는 태그만** — 아래 보충 표의 다섯 개. 회귀를 볼 거리가 있는지의 기준이지,
  태그별 통과율을 낼 수 있는 수는 아니다. 나머지는 자연히 나온 만큼:
  judge 태그는 edge 층이 채우고, 가려짐 · 손에 듦 · 잘림 · 워터마크 · 하자 같은 건 검색으로 노릴 수 없고, `private` 은 모을 이유가 없다
- 층 목표를 다 채운 뒤 `intake.py status` 태그 표에서 ⚠ 인 태그만 보충한다
  - 보충 표의 검색어를 위에서부터, §1 규칙 그대로 (최신순 첫 게시글 · 사진 전부 · 검색어당 게시글 3개)
  - **첫 사진에 노린 태그가 없어도 담는다** — "유리컵"의 첫 사진이 불투명 컵이면 그것도 담는다. 건너뛰기 시작하면 고르는 것이 된다
  - 태그는 게시글의 첫 사진에만 단다 (최소 수도 첫 사진으로 센다)
  - 그 태그가 최소 수에 닿으면, 하던 검색어를 게시글 3개까지 채우고 멈춘다. 표의 검색어를 다 써도 모자라면 멈추고 모자란 채로 둔다
  - 보충 사진은 `add --supplement` 로 넣는다 — **층 목표 밖 · 전부 dev**. 실패하기 쉬운 성격을 노려 모았으니
    test 에 넣으면 통과율이 실제보다 낮게 나온다. 층 코드는 사진을 보고 붙인다 (어느 층이든 목표는 안 줄어든다)
- 태그 표의 "파일럿·기존" 열은 참고만 — 기존 30장은 실패 모음에만 태그가 붙어 있어 (10-04 기준),
  다시 태깅하기 전에는 "태그가 있으면 실패한다"처럼 읽힌다

| 태그 | 보충 검색어 |
|---|---|
| `transparent` | 유리컵, 투명 케이스, 아크릴 스탠드 |
| `glossy_material` | 크롬 휠, 에나멜 구두, 페이턴트 가방, 나일론 바람막이 |
| `packaging` | 미개봉, 새상품 비닐 |
| `pattern` | 체크 셔츠, 프린트 티셔츠, 패턴 머그 |
| 여러 개 (`item_count ≥ 2`) | 일괄, 세트, 2개 |

## 3. 저장

1. 게시글마다 `backend/eval/data/images/inbox/` 안에 폴더를 하나 만든다. 폴더 이름: `<코드>_<아무거나>`
2. 그 폴더에 사진을 **게시글 순서대로** `1.jpg`, `2.jpg`, … 로 저장한다 (jpg · png · webp 만 — heic · gif 는 다시 저장.
   섞여 있으면 `add` 가 거부한다). 숫자 순서가 곧 게시글 순서다 — `1` 이 첫 사진
   - 예: `none_airpods/1.jpg`, `none_airpods/2.jpg`, `doc_linear_algebra/1.webp`
   - 사진이 한 장뿐인 게시글은 폴더 대신 `none_airpods.jpg` 파일 하나로 둬도 된다
   - 네이버 카페 이미지는 우클릭 → 이미지 저장 (주소로 내려받으면 막힐 때가 많다)
   - `add` 하면 `images/none_airpods_p01.jpg`, `_p02.jpg` … 로 옮겨진다
3. 게시글 주소를 `data/images/inbox/urls.txt` 에 한 줄씩: `폴더이름 주소` (마지막 칸이 주소 — 이름에 공백이 있어도 된다)

   ```text
   none_airpods https://cafe.naver.com/joonggonara/123456789
   doc_linear_algebra https://cafe.naver.com/joonggonara/123456790
   ```

4. 모인 만큼 정리한다 (중간중간 해도 된다)

   ```bash
   cd backend
   python eval/intake.py status          # 층별로 게시글 몇 개 모였나
   python eval/intake.py add             # inbox → images/, dataset.json 에 추가, dev/test 나눔
   python eval/intake.py add --supplement    # §2-1 보충 검색어로 모은 사진 (층 목표 밖 · 전부 dev)
   ```

   - test / dev 는 게시글 단위 — 한 게시글의 사진은 모두 같은 쪽으로 간다 (같은 물건이 양쪽에 있으면 새어 나간다)
   - `add` 가 라벨 달 항목(게시글의 **첫 사진만**)을 `data/images/inbox/labels.csv` 로 뽑아 준다.
     파일이 이미 있으면 **채워 둔 칸은 그대로 두고** 새 사진 줄만 더한다 — 라벨을 반쯤 달다가 사진을 더 모아도 된다
   - 하나라도 틀리면(이름 규칙 · 사진 번호가 1 부터 안 이어짐 · 같은 이름 · 같은 게시글 주소 · 첫 사진이 이미 있음 · 층 목표 넘음) 아무것도 옮기지 않는다

## 4. 라벨 (실행하기 전에)

`labels.csv` 를 스프레드시트로 열어 채운다. 기준은 `README.md` 의 "정답 라벨" 표.
기존 8장(초안 라벨 `claude-draft`)도 들어 있다 — 확인하고 고쳐 넣으면 이름이 바뀐다.

**엑셀 주의** — 엑셀은 `1-2` 를 날짜로, `1E5` 를 숫자로 바꾸고 앞자리 0 을 지운다. `key_texts` 는 그대로여야 할
글자라 이러면 정답이 틀어진다. `merge` 가 날짜·숫자처럼 보이는 값을 경고하지만, 모델명·숫자가 있으면
**데이터 → 텍스트/CSV 에서 → 열 형식 "텍스트"** 로 불러오거나 구글 시트에서 그 열을 "일반 텍스트"로 두고 채운다.
저장은 "CSV UTF-8" 이 좋다 (일반 CSV 로 저장해도 읽기는 한다).

| 열 | 값 |
|---|---|
| `category` | `shoes` / `clothing` / `bag` / `electronics` / `vehicle` / `other` / `watch` / `media` (`watch` · `media` 는 앱에선 other) |
| `photo_type` | `document` / `inside_view` / `product` |
| `wear_level` | `none` / `light` / `heavy` — 앱 분석이 아직 이 값을 써서 기준선까지는 그대로. 분석을 바꿀 때 "넓은 흔적 있음 / 없음"으로 바꾼다 |
| `text_level` | `none` / `simple` / `dense` |
| `key_texts` | 결과에서 그대로여야 할 글자 — 여러 개면 `\|` 로 구분 (예: `선형대수\|WILEY`) |
| `item` | 짧은 영어 명사 (참고용) |
| `item_count` | 팔 물건 개수 — 빈칸이면 1. 2 이상이면 eval 에서도 배경 제거만 |
| `edge_tags` | §2-1 태그, 여러 개면 `\|` 로 (예: `hand_held\|occluded`) |
| `ambiguous` | 판단이 애매하면 `y` — 나중에 따로 집계한다 (report 에는 아직 없음) |
| `note` | 자유 |

```bash
python eval/intake.py merge data/images/inbox/labels.csv --by <이름>
```

- 값이 하나라도 틀리면 전부 반영하지 않는다 (대소문자는 안 가린다). 빈 줄은 건너뛴다
- test 사진의 사람 라벨은 한 번 달면 바꾸지 않는다 — 결과를 보고 정답을 옮기지 않게. 정말 틀렸으면 `--relabel`
- 층(파일 이름 코드)과 라벨이 달라도 된다 — 집계는 라벨 기준이다. 층은 "모을 때의 의도"
- 20장 정도는 다른 사람도 따로 라벨을 달아 두면 라벨 자체가 흔들리는지 볼 수 있다

## 5. 걸리는 시간

게시글 하나에 폴더 만들기 + 사진 저장(평균 5장 가정, 장당 15초) + 주소 → 약 2분 → 125개 약 4시간 (몇 번에 나눠서).
라벨은 첫 사진만, 한 장에 30초 → 약 1시간.
