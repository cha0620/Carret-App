## 0. 한 줄 요약

판매자가 올린 사진에서 **팔 물건을 고르고**, **정답 구도를 고르고**, **[AI로 정리하기](생성)** 또는
**[배경만 바꾸기](원본 픽셀)** 중 하나를 고른다. 생성은 검사 → 1회 재생성까지만 하고 결과를 정직하게 표시한다.
틀린 곳은 칠해서 고치고, 최종본은 판매자가 확정한다. 모든 선택 · 피드백은 DB 에 남아 다음 판단의 근거가 된다.

## 2. 변환 파이프라인 (`backend/app/services/pipeline/`)

```
load → analyze → plan ─┬─ 생성:      [read_text] → generate → validate_result → score_similarity → verify ─┐
                       ├─ 배경 교체: composite                                                            ├→ save_inspect → finalize
                       └─ 원본 그대로: keep_original                                                     ┘
```

### 2-1. analyze — 원본 분석 (`analysis.py`, Gemini 3.8-flash high, 1회)

받는 것: 물건 이름 · **아이덴티티 마크**(로고 · 그래픽 · 글자, `size: small/large` · `on: main/component/accessory`) ·
물건 위치 · 사진 종류(`product` / `document` / `inside_view`) · 하자 수준(`none/light/heavy`) · 워터마크 ·
글자 수준(`none/simple/dense`) · 물건 목록(`objects`: 이름 · 박스 · 역할 · 팔 물건인가) · 겹침(`pieces_overlap`) · 잘림.
2회 실패하면 `detect_failed`. 결과는 `quality/{file_id}_analysis.json` 에 캐시.

하자는 **목록이 아니라 수준만** 본다 — 목록으로 "지켜라" 하면 생성이 하자를 지우거나 지어냈다 (09-27).

### 2-2. 판매자 선택 반영 (`selection.py`)

- 고르면(`sell` · `mains`): 고른 것 전부를 사진에, 안 고른 건 `leave_out`(프롬프트 "빼라") · `leave_out_boxes`(배경 교체에서 지움)
- 안 고르면: **본체 하나**(`rep_split`), 나머지 구성품 · 상자는 `detail_pieces`(결과 아래 검증 목록)
- 세트 구성품 세기 `set_pieces` — 같은 종류는 번호를 떼고 묶어 센다

### 2-3. plan — 갈림길 (`routing.py`)

먼저 **위험 이유**를 찾는다 (`_composite_first_reason`): 분석 실패 · 내부 사진 · 문서 · (글자 판단이 켜졌을 때만) 잔글씨 ·
하자 많음 · 잘림 · 구성품 겹침 · 여러 개.

| 판매자 선택 (`user_mode`) | 동작 |
|---|---|
| `generate` | **어떤 이유가 있어도 생성.** 이유는 `risk_reason` 으로만 남는다 (나중에 "이유별 실패율" 근거) |
| `composite` | 배경 교체. 이유가 없으면 `user_choice` |
| 없음 (옛 호출 · eval `--mode auto`) | 예전처럼 이유가 있으면 배경 교체 · 원본 그대로 |

### 2-4. generate — 생성 (`generation.py`, fal `flux-2/flash/edit` 8스텝)

앱은 `clean_prompt="set"`:

- **물건 하나** → 최소 프롬프트 `MIN_PROMPT`: "Image 1 is the item. Photograph the item from image 1 exactly as it is, …" +
  배경 + (정답을 골랐으면) 선 그림 + 구도 문장 + 빼라. 나열 · 금지 · 이름을 덧붙이지 않는다 — 덧붙일수록 흔한 모양을 끌어왔다 (10-09)
- **고른 게 2개 이상(세트)** → 종류 · 개수 JSON(`set_prompt`) + 배치 문장(`plan_layout`: 정답 사진을 보고 모델이 이 구성품에 맞게 한두 문장).
  선 그림은 넣지 않는다 — 그림 속 다른 레고를 베꼈다 (10-09). 입력은 기준 + 같은 세트 다른 사진 2장까지
- 정답 = **선 그림 + 동작 문장** (`style_refs.json` 의 `layout`) — 문장은 "똑바로 세워" 같은 동작 · 배치만, 디테일 묘사 금지
- 재생성 때는 사라진 마크 이름을 프롬프트에 붙인다 (생긴 글자는 이름을 쓰지 않는다 — 쓰면 그걸 다시 그렸다)

### 2-5. 생성 뒤 검사 (`checks.py`)

| 검사 | 모델 | 떨어지면 | 지금 |
|---|---|---|---|
| **사진 성립** (`check_photo`): 물건이 잘렸나, 자막 · 글자가 가렸나 | Gemini lite | 다시 생성 (최대 `MAX_GENERATE_ATTEMPTS`=2) | 켜짐. 호출 실패는 통과 |
| **마크 보존** (`verify_and_locate`): 원본 로고 · 마크가 그대로인가 (체크리스트, 좌표 `box_2d`) | Gemini high | 1회 재생성 | 켜짐. **글자 앵커는 뺀다** (`text_gate=false`) |
| 없던 글자 · 로고 (`added_text`) | Gemini | 1회 재생성 | **꺼짐** (`text_gate=false`) |
| 구성품 개수 (`count_pieces`) | Gemini | 1회 재생성. 호출 실패도 탈락 | 앱 꺼짐 (`COUNT_GATE`), eval 켜짐 |
| 관측 신호: 전체 DINO · (켜면) 로컬 OCR · 누끼 비교 `item_dino` · `item_patch` | 로컬 | 막지 않음 (soft) | 누끼 비교는 응답 뒤 백그라운드 |

**검사 뒤 갈림 (`_route_after_verify`)**

- 생성 모드: 떨어지면 1회 재생성 → 그래도 떨어지면 **마지막 결과 + 탈락 기록**으로 끝. 배경 교체로 몰래 바꾸지 않는다 (10-11)
- 검사 호출 자체가 실패 (`verify_failed`) · 분석 실패: 생성 모드면 재생성 없이 내보내고 화면에 "검사 못 함"
- 모드 없음(옛 호출): 예전처럼 2번째 실패면 배경 교체

### 2-6. 배경 교체 (`composite.py`)

원본 물건을 오려(fal BiRefNet, 실패하면 rembg) 프리셋 배경 위에. 물건 픽셀은 원본 그대로.
문서는 네 모서리를 찾아 정면으로 편다(`compose_flat`). 배경 교체 모드에서 오리기가 실패하면 생성으로 넘어가지 않고 원본 그대로.
알려진 한계: 고른 물건이 여럿인데 배경 교체로 가면 본체 영역만 남는다 (레고 피규어 잘림, 10-11).

### 2-7. 기록 (`results.py`)

`quality/{file_id}_{preset}_inspect.json` (경로 · 이유 · 검사 결과 · 프롬프트), DB `results` (경로 열 포함).
성적표(judge)는 **eval · dev 만** — 사람 판정과 17쌍 중 11쌍만 맞아 운영에서 뺐다 (10-05).

## 3. 글자 · 구도 · 정직함에 관한 지금 규칙

- **글자는 대표사진에서 판단하지 않는다** (`TEXT_GATE=false`, 10-11): 잔글씨여도 생성, 글자 읽기 · 글자 검사 · 없던 글자 검사 안 함.
  결과 아래 "글자 · 라벨 · 인증 스티커를 가까이 찍은 사진 (검증용)" 요청. 로고 · 마크 검사는 남는다
- **구도는 모델이 판단** (10-11): `detector.composition_check` 가 판매자 사진 + 정답 사진을 보고 "지어내지 않고 이 구도로 만들 수 있나,
  모자라면 어느 방면 사진이 필요한가". eval `run_posts.py --view-check` 에서 ok=false 면 **생성하지 않고 "구도 부족"으로 기록**
  (앱 연결은 아직). 앱의 사진 검토(`photo_review`)는 정답 사진 기준으로 "더 올리면 좋은 사진"을 준다
- **정직 표시** (`render.js`): 생성본 "AI 가 다시 그린 사진 · 흠집은 자동 검사하지 않아요", 위험 이유가 있었으면 "원본과 꼭 비교",
  배경 교체 "원본 물건 사진에 배경만", 검사 실패 · 못 함은 그대로 표시

## 4. 칠한 곳 고치기 A/B (`inpaint.html`, `routes/inpaint.py`, `ai/inpainter.py`)

1. 결과 위에 붓으로 칠하고 설명을 쓴다
2. 서버가 두 방식을 동시에 돌린다 — 어느 쪽이 A 인지 무작위, 고르기 전엔 숨김
   - **flash**: 결과 + 원본 + 마스크 사진을 넣고 "image 3 의 흰 영역만, {설명}, image 2(원본)에 맞춰라"
   - **Kontext 인페인팅** (`flux-kontext-lora/inpaint`): `mask_url` + `reference_image_url`(원본) + "{설명}. 원본에 맞춰라"
3. 두 결과 모두 **칠한 영역만** 원래 사진에 붙인다 (경계 4px 흐림) — 칠하지 않은 곳은 픽셀 그대로
4. 판매자가 고르면 모델 · 프롬프트 공개, 고른 사진이 다음 칠하기의 바탕. 같은 사진 동시 실행 막음(409), 마스크는 PNG · 크기 상한
5. 기록: DB `inpaint_rounds` (설명 · 고른 쪽 · 모델 · 칠한 면적), 마스크 그림은 storage

## 8. 열린 문제 (2026-10-11)

- 모양 · 없던 부분 · 복제를 보는 검사가 없다 (자전거 핸들 · 아이폰 없던 화면 · 에어팟 모양) — 원본 기반 질문 검사 후보 (`study/2026-10-11` §12)
- 마크가 0개면 마크 검사가 비어 통과한다
- 재생성 기준은 사용자가 다시 정하기로 함 (작은 표시 `size: small` 오탐 근거 있음)
- 고른 물건이 여럿인데 배경 교체로 가면 잘림 · 시즌그리팅 물건 묶기 JSON 깨짐
- 구도 검사(`composition_check`)는 eval 에만 — 판정이 맞는지 사용자 평가 후 앱 연결
- 정답 추천: 태그로 거르고 벡터(이 정답으로 하면 예쁘고 알맞게 나올지)로 순위 — 정답이 늘면
