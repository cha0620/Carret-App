# 2026-09-15 — Langfuse 도입 (프롬프트 관리 + 실제 트레이싱 + 품질 점수)

오늘 하루 세 단계로 진행했다: ① 프롬프트를 코드 밖(Langfuse 콘솔)으로 빼기 →
② 죽어있던 트레이싱 코드를 실제 v4 API로 살리기 → ③ judge 점수 + DINOv2 벡터
유사도를 Langfuse Score로 붙이기. 세 개 다 같은 원칙 하나를 공유한다 —
**"Langfuse 없으면(키 미설정) 완전 noop, 네트워크 호출 자체를 안 함. 있는데
실패해도 항상 로컬 fallback/무시로 계속 동작. 테스트/CI는 항상 첫 번째 케이스."**

## 1. 프롬프트 관리 (Langfuse Prompt Management)

### 문제
프롬프트(`classify`/`detect`/`verify`/`match`/`judge_system`/프리셋 3종)가
전부 `backend/app/prompts/**`와 `judge.py`에 파이썬 문자열로 박혀 있어서,
문구 하나 고치려면 코드 수정 + 배포가 필요했다.

### 설계
새로 만든 `backend/app/core/prompt_registry.py`가 유일한 진입점:

```python
from app.core.prompt_registry import get_prompt_text
text = get_prompt_text("judge_system", fallback=TEMPLATE, rubric=rubric_text())
```

1. `settings.langfuse_public_key`/`langfuse_secret_key`가 비어 있으면 →
   네트워크 없이 `fallback` 문자열에 변수만 로컬로 채워 즉시 반환.
2. 키가 있으면 `lf.get_prompt(name, label="production", fallback=fallback,
   max_retries=0, fetch_timeout_seconds=3)` → 성공하면 콘솔 텍스트, 실패
   (인증/네트워크/미등록 등 무엇이든)하면 SDK가 자동으로 `fallback`을 감싸서
   돌려준다. `.compile(**변수)`.
3. `max_retries=0` + `fetch_timeout_seconds=3`: 기본값(재시도 2회+백오프)이면
   Langfuse가 막혀 있을 때 최대 9초까지 걸렸다(실측: 실패 5연속 9.6초) —
   항상 안전한 로컬 fallback이 있으므로 재시도 의미 없음, 3초로 줄임(같은
   조건 재측정 2.1초).

변수 문법은 Langfuse 컨벤션인 이중 중괄호 `{{var}}` — 프롬프트 안 JSON 예시
(`judge_system`의 `{"fidelity": 1-5}` 같은 단일 중괄호)와 충돌 안 하게. 로컬
fallback 컴파일도 `str.format()`이 아니라 `"{{key}}"` 문자열 치환만 한다
(JSON 깨짐 방지).

### 적용 위치

| Langfuse 프롬프트 이름 | 코드 위치 | 변수 |
|---|---|---|
| `classify` | `app/prompts/__init__.py::classify_prompt()` | 없음 |
| `detect_box` | `app/prompts/__init__.py::detect_box_prompt()` | 없음 |
| `detect` | `app/prompts/__init__.py::detect_prompt(item, considered)` | `{{item}}`, `{{hints}}` |
| `verify` | `app/prompts/__init__.py::verify_prompt(anchors, item, considered)` | `{{item}}`, `{{checklist}}`, `{{lines}}` |
| `match` | `app/prompts/__init__.py::match_prompt(orig, result)` | `{{orig}}`, `{{result}}` |
| `judge_system` | `app/services/judge.py::_system_prompt()` | `{{rubric}}` |
| `preset_studio_white` / `preset_warm_wood` / `preset_minimal_gray` | `app/prompts/presets.py::get_preset(key)` | 없음 |

fallback 원본은 `app/prompts/fragments/*.md` + 각 모듈의 `_TEMPLATE` 문자열 —
**지우면 안 됨**(Langfuse 응답 못 할 때의 안전망). `CLASSIFY_PROMPT`/
`DETECT_BOX_PROMPT`는 상수→함수(`classify_prompt()`/`detect_box_prompt()`)로
바꿨다 — 상수면 프로세스 뜬 시점 버전에 영구 고정되고 모든 테스트가 import
시점에 네트워크를 타게 되어서.

### 사용법 (운영)
1. 최초 1회: `cd backend && python scripts/seed_langfuse_prompts.py` — 위 표
   7개 프롬프트가 현재 코드 fallback 텍스트 그대로 v1 등록 + "production"
   라벨. **재실행하면 매번 새 버전이 늘어남** — "코드 상태로 강제 리셋"할
   때만 다시 돌릴 것.
2. 이후 문구 수정은 콘솔 → Prompts → 이름 클릭 → New version → 변수는 꼭
   `{{item}}`처럼 이중 중괄호로(오타 나면 그 변수는 안 채워지고 텍스트
   그대로 남음) → 새 버전에 "production" 라벨 이동(라벨은 버전당 하나만,
   자동으로 이전 버전에서 빠짐).
3. 배포/재시작 불필요 — `get_prompt_text()`가 60초(SDK 기본 `cache_ttl_seconds`)
   캐시하므로 저장 후 최대 1분 안에 반영. 롤백도 이전 버전에 라벨만 다시
   붙이면 끝.
4. 안전망 확인: `LANGFUSE_PUBLIC_KEY`/`SECRET_KEY`를 비우면 100% 로컬
   fallback만 동작(네트워크 자체를 안 탐 — `get_langfuse()`가 `None`).

## 2. 실제 트레이싱 (Langfuse v4 OTEL API)

### 문제
`backend/app/core/tracing.py`에 `get_langfuse()`(클라이언트 싱글톤)는 이미
prompt_registry가 재사용 중이었지만, 트레이싱 함수(`start_trace`/`span`/
`generation`/`end`/`fail`)는 `lf.trace()` 같은 **v2 API**로 짜여 있었는데
실제 설치본은 `langfuse==4.15.2`(v2엔 없는 메서드라 호출하면 AttributeError)
— 그리고 앱 어디서도 import 안 되는 죽은 코드였다. 즉 파이프라인을 돌려도
Langfuse 콘솔엔 프롬프트 조회 로그만 찍히지, "요청이 몇 초 걸렸고 어떤 VLM
호출들로 구성됐는지"는 전혀 안 보였다.

### 설계: OTEL 컨텍스트 매니저 하나로 통일
v4 SDK는 OTEL 기반이라 트레이스 객체를 직접 들고 다닐 필요가 없다 —
`start_as_current_observation(...)`로 들어간 블록 안에서 또 다른 걸 부르면
자동으로 부모-자식으로 중첩된다. `tracing.py`에 컨텍스트 매니저 하나만
새로 만들었다:

```python
from app.core.tracing import observe

with observe("detect", as_type="generation", model=MODEL, input=prompt) as obs:
    resp = call_vlm(...)
    if obs is not None:
        obs.update(output=resp, usage_details={...})
```

`get_langfuse()`가 `None`(키 미설정)이면 `observe()`는 `yield None`만 하는
진짜 noop. 호출부는 전부 `if obs is not None:` 가드 뒤에서만 `.update()`를
부르므로 트레이싱 꺼져 있을 때 반환값/부작용은 이전과 100% 동일(테스트로 확인).

싱글톤 초기화(`get_langfuse()`의 `_client`)는 FastAPI 스레드풀에서 동시
요청이 첫 호출을 같이 탈 수 있어 `threading.Lock` double-checked locking으로
보강했다(코드 리뷰에서 지적됨 — 3번 참고).

### 적용 위치

| observation 이름 | as_type | 코드 위치 | 비고 |
|---|---|---|---|
| `transform` | span (루트) | `pipeline.py::run_transform()` | file_id/preset_key 메타데이터, `pipeline_mode="mock"` 지름길은 트레이싱 없음 |
| `transform_dev` | span (루트) | `pipeline.py::run_transform_with_result()` | dev 전용, generate 건너뜀 |
| `classify` | generation | `detector.py::classify()` → `_call(..., "classify")` | |
| `detect` | generation | `detector.py::detect_defects()` → `_call(..., "detect")` | |
| `verify` | generation | `detector.py::verify_and_locate()` → `_call(..., "verify")` | |
| `detect_with_boxes` | generation | `detector.py::detect_with_boxes()` | 측정 경로(eval 전용) |
| `match` | generation | `detector.py::match_anchors()` | 측정 경로(eval 전용) |
| `judge` | generation | `judge.py::judge()` | fidelity/realism/trust는 output JSON + Score 둘 다(3번) |
| `generate_image` | generation | `generator.py::_generate_ai()` | fal.ai 호출 |
| `dino_similarity` | embedding | `embedder.py::cosine_similarity()` | 3번 참고 |

`transform` 루트 span이 LangGraph `GRAPH.invoke(...)`를 감싸는 동안, 안에서
실행되는 노드들이 부르는 VLM/임베딩 호출들이 OTEL contextvars로 자동
중첩된다 — 코드에서 트레이스 객체를 수동으로 넘길 필요 없음. (리뷰에서
LangGraph의 `BackgroundExecutor.submit()`이 `copy_context()`로 호출 스레드의
contextvars를 스냅샷해서 워커 스레드에 넘긴다는 것까지 소스 레벨로 확인함 —
노드가 다른 스레드에서 돌아도 트레이스 귀속이 깨지지 않음.)

각 VLM generation은 `resp.usage_metadata`를 `usage_details`로 같이 보낸다.
이 변환 로직(`gemini_usage()`)은 원래 `detector.py`/`judge.py`에 중복
구현돼 있었는데, 리뷰 지적으로 `tracing.py`에 공용 함수로 합치고 양쪽에서
import해서 쓰도록 정리했다(`detector.py`는 하위호환으로 `_usage` 이름을
그대로 유지 — `from app.core.tracing import gemini_usage as _usage`).

`run_transform`/`run_transform_with_result`는 `try/finally`로 감싸 **성공이든
예외든 항상 `flush()`가 실행**되게 했다 — 원래는 `with observe(...)` 블록
정상 종료 시에만 flush가 실행돼서, 정작 가장 보고 싶은 "실패한 요청"의
트레이스가 배치 주기까지 안 나가고 프로세스 종료로 유실될 수 있었다(리뷰
발견, 즉시 수정).

## 3. Score: judge 축 점수 + DINOv2 벡터 유사도

Langfuse의 "Score"는 `generation`의 `output`과 별개 개념 — 트레이스/span에
매다는 채점값(`name`, `value`, `data_type: NUMERIC|CATEGORICAL|BOOLEAN|TEXT|CORRECTION`)이고
콘솔 트레이스 목록에 전용 컬럼으로 떠서 필터/정렬/대시보드 집계가 된다.
`tracing.py`에 헬퍼 하나 추가:

```python
def score(name: str, value, **kw):
    lf = get_langfuse()
    if lf is not None:
        lf.score_current_trace(name=name, value=value, **kw)
```

**3-1. judge 축 점수** — `pipeline.py::run_judge()`가 `judge.judge()`를 새로
계산했을 때(캐시 hit이면 스킵 — 캐시는 이번 트레이스에서 재계산한 게
아니므로) `AXES`(fidelity/realism/trust, `app/prompts/rubric.py`) 3개를
각각 `score(axis, report[axis], data_type="NUMERIC")`로 `transform` 트레이스에
부착. 이 루프는 자체 `try/except`로 감쌌다(SDK 내부적으로도 예외를 삼키긴
하지만, 파일의 다른 노드들이 전부 자체 방어를 하는 컨벤션과 맞춤).

**3-2. DINOv2 벡터 유사도** — 새 `app/services/embedder.py`. VLM judge는
"판단"이라 프롬프트/모델 버전에 흔들릴 수 있는데, DINOv2 코사인 유사도는
API 호출 없이 로컬 모델 하나로 고정된 축을 재는 값이라 상대적으로 안정적 —
judge를 대체하지 않고 보완하는 신호.

```python
sim = embedder.cosine_similarity(orig_bytes, result_bytes)  # 0~1, 원본↔결과 구조적 유사도
```

- 모델: `facebook/dinov2-small`(transformers `AutoModel`, CPU). 모듈 전역
  lazy 싱글톤으로 캐시(첫 호출에서만 로드 — 이후 재사용). 동시 요청이 첫
  호출을 같이 탈 수 있어 `get_langfuse()`와 동일하게 `threading.Lock`
  double-checked locking으로 보강(리뷰 발견, 안 하면 모델이 두 번 로드돼
  메모리 낭비).
- 각 이미지의 CLS 토큰(384차원) → L2 정규화 → 내적 = 코사인 유사도.
- 파이프라인에 새 노드 `score_similarity`를 `generate`와 `verify` 사이에
  삽입: `load → classify → detect → generate → score_similarity → verify →
  save_inspect → run_judge → finalize`. 실패해도(이미지 디코딩 실패, 모델
  로드 실패 등) 다른 노드들과 같은 "실패(무시)" 컨벤션으로
  `{"visual_similarity": None}`을 반환하고 계속 진행.
- 결과는 `state["visual_similarity"]`로 전체 State에 실려 `save_inspect`의
  디버그 JSON(`storage/quality/{file_id}_{preset}_inspect.json`)에도 기록되고,
  `visual_similarity`라는 이름의 Langfuse NUMERIC 점수로도 `transform`
  트레이스에 부착된다. **`TransformResponse`(API 응답 스키마)에는 아직 안
  넣었다** — 지금은 관측용(콘솔/디버그 JSON)으로만 쓰고, 프론트에 노출할
  필요가 생기면 그때 스키마/라우트를 따로 손보기로 함(범위 밖으로 남겨둠).

### 의존성
`torch`/`torchvision`/`transformers`를 CPU 전용 wheel로 추가했다 — 이 배포
환경엔 GPU가 없는데 기본 PyPI index로 `pip install torch`를 하면 CUDA
런타임(수 GB)까지 딸려온다. `Dockerfile`에서 `--index-url
https://download.pytorch.org/whl/cpu`로 먼저 깔고, 이후 `-r requirements.txt`가
같은 버전 제약을 보고 스킵하게 순서를 맞췄다. 로컬 venv에도 CPU wheel로
설치해서 로드+추론(64×64 테스트 이미지 기준 로드 ~17초/첫 1회, 추론 ~0.3초)
확인함.

## 4. 코드 리뷰에서 발견/수정한 것

reviewer 서브에이전트로 diff 리뷰(2번+3번 전체) 돌려서 나온 것 중 이번
세션에서 바로 고친 것들:

1. **`flush()`가 예외 경로에서 스킵됨** — 위 2번 마지막 문단, 수정 완료.
2. **`detector.detect_defects()` 시그니처 파괴** — (이번 세션 작업은 아니고
   이전 세션의 classify 기능 추가 때 생긴 버그) `item`/`considered`에 기본값이
   없어서 `app/api/routes/dev.py`, `app/util/evaluator.py`(2곳),
   `scripts/run_dector.py`가 인자 1개만 넘기던 기존 호출이 전부
   `TypeError`로 깨져 있었음 — `/dev/detect`, `/dev/eval-*` 엔드포인트와
   스크립트가 실제로 죽는 상태였다. `item: str = "object", considered: list
   | None = None`으로 기본값을 넣어 고침.
3. **싱글톤 스레드 안전성** — `tracing.get_langfuse()`, `embedder._load()`
   둘 다 `threading.Lock` double-checked locking 추가(위에서 설명).
4. **`_usage()` 중복** — `detector.py`/`judge.py`에 각각 따로 있던 동일 로직을
   `tracing.gemini_usage()`로 합침.
5. **`run_judge`의 score 루프에 방어 없음** — `try/except` 추가(컨벤션 일관성).

리뷰에서 지적됐지만 **일부러 안 고친 것**:
- `embedder.py::embed()`의 `import torch`를 모듈 최상단으로 옮기라는 제안 —
  **거부**. `pipeline.py`가 `embedder`를 모듈 로드 시점에 import하므로, 최상단
  으로 옮기면 앱 기동/테스트 수집마다 항상 300MB+짜리 torch를 즉시 로드하게
  되어 지금의 "실제로 유사도를 계산할 때만 로드" lazy 전략이 깨진다. 함수
  내부 lazy import를 유지.
- `score_similarity`의 "계산 실패"와 "트레이싱 업데이트 실패"가 하나의
  `try/except`로 뭉쳐 있는 것 — 분리하면 더 안전하지만 `obs.update()`가
  동기 I/O를 안 해서 실제 위험도가 낮다고 판단, 이번엔 보류.
- `visual_similarity`를 `TransformResponse`에 노출하는 것 — 위 3-2 참고,
  범위 밖으로 남김.

## 5. 테스트
tester 서브에이전트가 새 tracing/score/embedder 계측에 대한 단위테스트를
작성 — 기존 `test_judge.py`/`test_presets.py`/`test_prompt_registry.py`가
쓰던 `tracing._client=None`/`tracing._disabled=True` monkeypatch 컨벤션을
그대로 따름(비활성 경로), 활성 경로는 가짜 Langfuse 클라이언트로 검증.
새 파일: `test_tracing.py`, `test_embedder.py`, 기존 `test_detector.py`/
`test_judge.py`/`test_generator.py`/`test_pipeline.py`에 계측 관련 케이스
추가. 실제 DINOv2 모델/네트워크는 전부 모킹 — 테스트는 무거운 모델을 안 띄움.

**최종: 129개 테스트 전부 통과**(`test_browser.py`의 playwright `page`
fixture 미설치 건 1개는 이번 작업과 무관한 기존 실패, 매번 별도로 제외).

## 6. 확인된 부작용 / 아직 안 풀린 문제

- **Langfuse 키 401** — `.env`의 `LANGFUSE_PUBLIC_KEY`/`SECRET_KEY`가 순서는
  맞춰놨지만(지난 세션에 뒤바뀐 것 고침) 여전히 인증 자체가 401(만료/폐기로
  추정, `cloud.langfuse.com`/`us.cloud.langfuse.com` 둘 다 동일). 테스트나
  실행 중 배경으로 `Failed to export span batch code: 401` 경고가 뜨는데
  이건 무해한 비동기 워닝이고 fallback으로 정상 동작한다. **새 키를 받으면**
  `.env` 반영 + `scripts/seed_langfuse_prompts.py` 재실행까지 해야 이번 작업
  전체(프롬프트 관리+트레이싱+Score)가 실제로 콘솔에 "켜진다".
- **S3 AccessDenied — 새로 발견, 미해결.** "패턴 잡아보자"며 실제 원본
  이미지 3장으로 `pipeline.run_transform()`을 직접 돌려봤는데, fal.ai
  생성까지는 성공(비용 발생함)하고 `storage.save("result", ...)`에서
  전부 실패:
  ```
  AccessDenied: User arn:aws:iam::725171146931:user/carret-app is not
  authorized to perform s3:PutObject on resource
  "arn:aws:s3:::carret-app/carret/result/..."
  ```
  `STORAGE_BACKEND=s3`인데 그 IAM 유저에 해당 버킷 PutObject 권한이 없다 —
  이번 세션의 트레이싱/DINO 작업과 무관한 순수 인프라 문제. `generate` 노드가
  여기서 예외로 죽어서 `score_similarity`/`verify`/`judge` 단계까지 못 가고,
  그래서 아직 "실 데이터로 점수 패턴 확인"은 못 했다. 사용자가 "이번 실험만
  로컬 스토리지로 우회"를 선택함 — **다음 세션에서 `STORAGE_BACKEND=local`로
  임시 오버라이드해서 재시도 예정**(`.env`는 안 건드리고 스크립트 실행
  시점에만 덮어씀). IAM 정책 자체 수정은 사용자의 AWS 콘솔 작업이 필요해서
  별개로 남겨둠.

## 7. 수동 샘플 3건 결과 (S3 우회로 재실행)
`storage.BACKEND`를 스크립트 실행 중에만 `LocalBackend()`로 덮어써서(`.env`
불변, IAM 문제 우회) `run_transform()`을 실제 이미지 3장으로 돌렸다.

| 샘플 | item | fidelity/realism/trust | gate_passed | visual_similarity | 비고 |
|---|---|---|---|---|---|
| 473f... | car | 4/5/5 | **False** | 0.807 | 실패 원인 앵커 1개 = "벽의 한글 텍스트"(배경, 상품 아님) |
| 7222... | sweater | 4/5/5 | **True** | 0.914 | 앵커 3개 전부 보존 |
| 6679... | t-shirt | **5**/5/5 | **False** | 0.985 | judge는 만점인데 verify가 앵커 5개 중 3개(변색, 밑단 헤짐 2곳) 실패 |

**gate_passed 판정 로직** (`detector.all_preserved()` + `pipeline.py::verify`):
`detect_defects()`가 원본에서 뽑은 결함 앵커 리스트를, `verify_and_locate()`가
결과 이미지를 보고 앵커 하나하나 `preserved: true/false`로 재판정 →
`all(preserved)` AND 조건이라 **앵커 하나라도 false면 전체 게이트 실패**.
앵커 개수가 많을수록/detect가 오탐할수록 실패 확률이 올라가는 구조.

**패턴 2개, n=3이라 가설 수준:**
1. **detect가 배경 요소를 상품 결함으로 오탐.** car 케이스의 유일한 실패
   항목이 차량이 아니라 배경 벽의 텍스트 — 배경을 스튜디오로 바꾸면 당연히
   사라지는데 게이트가 이걸 실패로 잡는다. `detect` 프롬프트를 "상품 자체만"
   으로 더 타이트하게 제한하면 개선 여지 있음.
2. **judge(전체 인상)와 verify(개별 앵커)가 갈릴 수 있음.** t-shirt는 judge
   fidelity 만점인데 verify는 앵커 5개 중 3개를 실패로 판정해서 게이트가
   떨어짐 — 두 메커니즘이 다른 기준으로 보고 있다는 신호.
3. DINO `visual_similarity`는 이 3개에서 `gate_passed`와 깔끔한 상관관계가
   없었음(최고값 0.985도 실패, 최저값 0.807도 실패, 중간값 0.914만 통과) —
   표본을 늘려야 판단 가능.

## 8. 테스트 결과 관리 — 이번엔 Langfuse만 쓰기로 결정
"판단(judge)/게이트(gate_passed)/벡터 유사도(DINO) 결과를 여러 번 돌린 걸
모아서 추이를 어떻게 관리하냐"는 질문에, 두 옵션(① Langfuse에 맡기기 ②
`scripts/run_eval.py`류의 로컬 하네스를 품질 축에도 하나 더 만들기)을 놓고
**① Langfuse만 우선 진행하기로 결정**. 로컬 하네스는 안 만듦 — 이미 모든
계측(트레이스+`fidelity`/`realism`/`trust`/`visual_similarity` Score)이
붙어 있으므로, 남은 건 순전히 "키가 살아있느냐"의 문제. 새 키를 받아서
`.env`에 반영하고 나면 콘솔에서 트레이스 목록 + Score 컬럼으로 바로 추이를
볼 수 있다 — 추가 코드 작업 불필요.

## 9. 새 키 반영 (2026-09-15 후속)

사용자가 새 Langfuse 키를 발급받아 `.env`에 반영. 확인하는 김에 진짜 원인을
하나 찾음:

**버그 — `LANGFUSE_HOST` ≠ `LANGFUSE_BASE_URL`.** `config.py`의
`langfuse_host` 필드는 pydantic-settings 기본 규칙상 `LANGFUSE_HOST` 환경
변수만 읽는데, `.env`엔 계속 `LANGFUSE_BASE_URL=https://us.cloud.langfuse.com`
로 적혀 있었다 → 이름이 안 맞아서 이 값이 **한 번도 로드된 적이 없고**,
`langfuse_host`는 항상 기본값 `https://cloud.langfuse.com`(EU)이었다. 6번에서
"EU/US 둘 다 401 동일"이라고 관찰한 것도 사실 둘 다 EU로 갔던 것 — 리전
설정 자체가 무의미했다. `Field(validation_alias=AliasChoices("LANGFUSE_HOST",
"LANGFUSE_BASE_URL"))`로 두 이름 다 인식하게 고침(다른 코드가 `LANGFUSE_HOST`를
쓸 가능성 대비 하위호환 유지).

고친 뒤 확인:
- `settings.langfuse_host` → `https://us.cloud.langfuse.com` 정확히 반영.
- `get_langfuse().auth_check()` → `True`.
- `scripts/seed_langfuse_prompts.py` 재실행 → 7개 프롬프트 v1(production) 등록 성공.
- `observe()`/`score()`/`flush()` 스모크 테스트 → 401 경고 없이 정상 전송.
- 전체 유닛테스트 재실행 → 전부 통과(config 변경으로 인한 회귀 없음).

이번 세션의 유일한 블로커였던 "키 401" 문제 해소 — 프롬프트 관리/트레이싱/
Score 세 가지가 이제 실제로 콘솔에 "켜진" 상태.
