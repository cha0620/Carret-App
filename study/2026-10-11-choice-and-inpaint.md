## 1. 대표사진 = 본체 하나 (상자도 뺌)

세션 시작 브리핑이 "남은 일 (없음)" 이었다 — 10-10 노트의 할 일이 들여쓴 체크 항목(앞에 공백 두 칸)이라
`.claude/hooks/session-brief.sh` 의 `^- \[ \]` 가 못 잡았다. 앞 공백 허용으로 고침.

사용자 결정: "본체만 첫 사진으로, 구성품들은 밑에 검증용으로 넘기거나 원하면 따로 소규모로 생성".
10-10 의 "대표 하나 + 상자" 를 한 번 더 좁혔다.

- `pipeline.rep_split` → `[본체]`, 나머지(상자 포함)는 `detail_pieces` (화면 `repSplit` 도 같게)
- `detail_pieces[].indices` 추가 — 화면이 구성품마다 [따로 만들기] (`separate=true`, 누를 때만 생성)
- 본품 이름이 "box"(보드게임 상자)면 말(구성품)을 본체로 고르던 것 → 분석 role=main 상자를 본체로
- **틀렸던 것**: 화면 확인에서 "물건 목록이 빔" 을 원래 있던 문제일 수 있다고 보고했는데,
  제 `repSplit` 이 빈 목록에서 `undefined` 를 돌려 생긴 오류였다. 고친 뒤 7개 정상

## 2. 배경 교체를 강제하지 않고 판매자가 고른다

사용자: "배경교체를 강제하기보단 유저에게 선택지를 주고, 생성이 잘 안될 가능성을 퍼센트로".

- 화면: [AI로 정리하기] · [배경만 바꾸기] 두 버튼. 위험 이유(잘림 · 겹침 · 여러 개 · 잔글씨 · 하자 · 문서)면
  ⚠️ 이유 + [배경만 바꾸기] 를 추천으로 강조. 생성도 누를 수 있다
- 서버: `TransformRequest.mode` → `State.user_mode`. `plan()` 이 생성을 고르면 위험이 있어도 생성,
  `risk_reason` 으로 남긴다. `inside_view` · `detect_failed` 는 고를 수 없다(검사할 기준이 없음)
- **퍼센트는 보류** — 저장된 inspect 126건: 생성 102건 중 27건이 게이트 탈락(약 26%).
  하지만 지금까지 강제로 배경 교체한 이유들은 생성을 한 번도 안 해 봐서 실측이 없다.
  사용자: "기록으로 하긴 할 건데 나중에 정하자" → `risk_reason` + 게이트 결과가 쌓이면 그걸로

## 3. 칠한 곳 고치기 A/B (`inpaint.html`)

사용자: "사진을 받고 특정 부분을 칠하고 그 부분을 설명하면 다시 생성 — 차라리 이게 나을 듯".
실패 확률을 맞히기보다 판매자가 틀린 곳을 짚는 쪽.

모델 조사 (fal, 마스크 · 원본 참고 지원 여부):

| 후보 | 마스크 | 원본 참고 | 결정 |
|---|---|---|---|
| `flux-2/flash/edit` (지금 모델) | 없음 → 마스크를 3번째 사진으로, 칠한 곳만 서버가 붙임 | ✅ | A/B 의 한쪽 |
| `flux-kontext-lora/inpaint` | ✅ | ✅ `reference_image_url` | A/B 의 다른 쪽 |
| `flux-pro/v1/fill` · `qwen-image-edit/inpaint` | ✅ | ❌ | 뺌 |

FLUX.2 전용 마스크 엔드포인트는 못 찾음. B 단가는 공식 페이지에 없음.

- 흐름: 칠하기 → [A · B 만들기] (둘을 같이, 어느 쪽인지 무작위 · 숨김) → 고르면 모델 · 프롬프트 공개 →
  고른 사진이 다음 칠하기의 바탕. 두 쪽 다 **칠한 영역만** 붙인다 (`inpainter.paste_back`, 경계 4px 흐림)
- 프롬프트 — 처음엔 "원본에 맞춰라" 를 넣었다가 사용자 말을 잘못 알아듣고 빼 버렸다.
  사용자 정정: **고정 "원본에 맞춰라" + 사용자 설명**

  | 방식 | 프롬프트 | 한국어 |
  |---|---|---|
  | flash | `In image 1, change only inside the white area of image 3: {note}. Match image 2, the original photo of the same item.` | 사진 1 에서 사진 3 의 흰 영역 안만 바꿔라: {설명}. 사진 2(같은 물건의 원본 사진)에 맞춰라 |
  | Kontext | `{note}. Match the reference photo, the original of the same item.` | {설명}. 참고 사진(같은 물건의 원본)에 맞춰라 |

- 기록은 **DB `inpaint_rounds`** (피드백의 한 종류 — 사용자). 마스크 그림만 storage `quality/{file_id}_ip{round}_mask.png`
- 실제 fal 호출은 아직 0회. Kontext 마스크 색(흰색 = 고칠 곳?)은 첫 실행에서 확인

## 4. "얼마나 일치하나" 지표 다시 세우기 — 추천

처음 목표는 "원본과 얼마나 일치하나" 였다. 지금 쓰는 DINO · item_dino 는 모양만 보고 색 · 질감 · 글자를
덜 본다 (DreamBench++ 가 같은 지적). 추천 — 세 층:

1. **주지표 = 판매자가 고친 비율** (사람): 결과 중 칠하기를 한 비율 · 칠한 면적 · 회차.
   §3 의 DB 에서 바로 나온다. 0 이면 일치. 가장 정직한 정답
2. **자동 지표 = 원본 대조 세 칸** (SpotEdit · ProductConsistency 식):
   - 추가(없던 것이 생김) · 누락(있던 것이 사라짐) · 변형(색 · 모양 · 글자가 바뀜) 개수 — VLM 이 원본 · 결과를 같이 보고 센다
   - 글자는 이미 있는 `ocr_local_recall` 을 그대로 "변형" 칸에
3. **보조 = 물건 영역만 자른 DreamSim/DINO + 색 차(ΔE)** — 배경은 바뀌는 게 정상이라 물건 마스크 안에서만

2 의 VLM 판정을 1(사람이 칠한 곳)과 맞춰 보면 자동 지표의 오탐 · 놓침률이 나온다 — 그게 다음 측정 과제.

## 5. 이건 할루시네이션인가 — 연구 · 기술블로그 조사

그렇다. 이미지 편집에선 **없던 것을 지어내는 것(추가)** 과 **물건의 정체성이 바뀌는 것(identity drift)** 을 같이
할루시네이션 · 충실도(fidelity) 문제로 다룬다. 다만 단일 표준 지표는 없다 — 대부분 사람 평가나 LLM judge.

| 출처 | 어떻게 푸나 |
|---|---|
| eBay 배경 교체 (09-27 노트) | 물건은 다시 그리지 않는다 — 오린 원본 위에 배경만 생성. 우리 "배경만 바꾸기" 와 같다 |
| Amazon, *Preserving Product Fidelity…* (2503.08729) | 여러 장 생성 → 물건만 자른 CLIP-I · DINO 합으로 순위 → 위만 남김. 통과율 상대 30.9% ↑ |
| *ProductConsistency* (2606.19103) | 로고 · 모양 · 글자의 작은 오류도 쓸 수 없다고 보고 SFT + RL 로 모델 자체를 학습. 평가는 LLM judge(일관성 · OCR · 미감) |
| *RefAdGen* (2508.11695) | 마스크 가이드 + 원본 참조 attention — 물건별 학습 없이 |
| *SpotEdit* (2508.18159) | 할루시네이션 전용 분할: 참조에 없는 물건을 넣으라 하면 "그대로 둔 것" 이 정답 |
| *DreamBench++* (2406.16855) | DINO · CLIP 이 사람 판단과 덜 맞는다 → 사람에 맞춘 judge |

우리 위치: 모델 학습(ProductConsistency)은 범위 밖. **안 그리기(배경 교체) · 여러 장 중 고르기(게이트) ·
사람이 짚어 고치기(§3)** 셋을 조합하는 쪽이 현실적이다.

## 9. "보증할 수 있는" 정직함 지표 — 공부

자료별 정리는 [`study/honesty-metric/`](honesty-metric/README.md) 폴더에 (자료 하나에 파일 하나).

사용자: 정직함은 "내가 보증을 설 수 있다" 급이어야 한다. 그러면 지표는 평균 점수가 아니라
**"통과시킨 사진 중 원본과 다른 사진이 ε 이하" 라는 약속**이어야 한다 — 틀린 통과율(false pass rate)의 상한.

### 9-1. 읽은 것 — 지금 쓰는 방식들은 보증이 안 된다

| 자료 | 방법 | 사람과 맞나 | 배운 것 |
|---|---|---|---|
| Amazon *Preserving Product Fidelity* (2503.08729) | 물건만 자른 CLIP-I · DINO 합으로 순위 | 사람 판정과 **Pearson 0.4** | 유사도는 거르는 데는 쓰지만 보증은 못 한다. 사람 통과율 자체가 17.4%(장) · 45.5%(물건) |
| *ProductConsistency* (2606.19103) | Seg CLIP-I · Seg DINO-I · OCR CER + GPT-5.1 judge(0~10, "7에서 깎기") | judge 를 사람과 **맞춰 보지 않음** | 유사도를 보상으로 쓰면 입력을 그대로 베껴 점수만 오른다(reward hacking) — 유사도 = 정직 아님 |
| DreamBench++ (2406.16855) | — | DINO 는 모양만, 색 · 질감을 덜 봄 | 지금 `item_dino` 의 한계와 같다 |
| VIEScore (ACL 2024) | VLM 점수 | 생성은 사람 수준, **편집에선 약함** | VLM 하나에 점수만 묻는 건 편집 검사로 부족 |
| ImgEdit-Judge (2505.20275) | 7B 를 20만 평가로 학습 | 사람 ±1점 안 약 70% (60장) | 학습해도 이 정도 |
| TIFA (ICCV 2023) · DSG (2310.18235) | 질문으로 쪼개 VQA 로 답하게 | TIFA ρ 0.60 vs CLIPScore 0.33. 사람끼리 α 0.88 | **쪼갠 질문**이 해석되고 사람과 더 맞는다 — DSG 는 질문 사이 의존(로고가 없으면 로고 글자 질문은 건너뜀)까지 |
| GIE-Bench · SpotEdit | 마스크 밖 보존 점수 · 할루시네이션 분할 | — | "바꾸지 말아야 할 곳" 을 따로 잰다 |

정리: 임베딩 유사도와 VLM 점수는 **순위 · 거르기 도구**이지 보증이 아니다. 보증은 사람 정답으로 잰 숫자에서만 나온다.

### 9-2. 보증은 어떻게 만드나 — 통계

보증 문장: "통과 배지를 단 사진 중 원본과 다른 점이 있는 것은 **ε 이하** (신뢰 95%)".
방법은 conformal risk control / Learn-then-Test 계열 — 사람이 라벨 단 보정 세트에서
틀린 통과율의 **신뢰 상한**(Clopper–Pearson)이 ε 아래가 되게 게이트 기준을 고른다.
유한 표본 · 분포 가정 없음. 단 **보정 세트와 같은 종류의 사진에만** 성립한다 (품목 · 경로별로 따로).

필요한 "통과 사진" 수 (직접 계산, 95% 단측):

| 약속 ε | 틀린 통과 0장일 때 | 1장 | 2장 |
|---|---|---|---|
| 10% | 29 | 46 | 61 |
| 5% | 59 | 93 | 124 |
| 2% | 149 | 236 | 313 |
| 1% | 299 | 473 | 628 |

→ 처음 목표는 **"5% 이하"를 품목 묶음별 통과 60~120장**으로. 1% 는 300장 넘게 필요해 당장은 무리.

### 9-3. Carret 에 맞춘 설계안 (아직 안 함)

1. **정의를 사진 단위 예/아니오로**: 원본과 다른 점(추가 · 누락 · 변형)이 하나라도 있으면 "다름". 점수가 아니라 이진 —
   보증 문장이 이진이라서
2. **정답 세트 (gold)**: 사용자가 직접 라벨. 판매자 확정(§8) · 칠하기(§3)는 후보를 모으는 통로이지 정답은 아니다
   (판매자가 못 보고 확정할 수 있다). 라벨은 세 칸 + 위치
3. **게이트 = 쪼갠 질문 (DSG 식)**: 원본에서 질문을 만든다 — 로고 · 글자 · 개수 · 색 · 하자 · 구성품마다 "결과에도 그대로인가".
   지금 있는 마크 · 글자 · 개수 게이트가 이 일부. 빠진 것: 색 · 하자 · "없던 것"
4. **기준 고르기**: gold 에서 틀린 통과율 상한 ≤ ε 인 가장 느슨한 기준 → 나머지는 배경 교체 추천.
   배경 교체는 물건 픽셀이 원본이라 따로 (오리기 경계만)
5. **화면에 표시**: 배지 옆에 "이 종류 사진 n장 검증 · 다른 점 있는 통과 ≤ ε" — 근거 수까지

남은 일:

- [ ] 정답 세트 라벨 방식 정하기 (세 칸 + 위치, 누가 · 몇 장) — 사용자와
- [ ] 지금 게이트(마크 · 글자 · 개수)의 틀린 통과율을 저장된 결과로 먼저 재기 (라벨만 있으면 무료)
- [ ] Conf-Gen (2605.28920) · CRC-Derive(ICML 2026) 원문 — 보증 방식 세부

## 11. 글자는 판단에서 빼기 · 구도 검사는 모델에게 · 생성 / 배경 교체 분리

사용자 결정 세 가지:

1. **글자는 어느 정도 무시** — 재생성 · 배경 교체 판단에서 빼고 상세(검증) 사진으로 보강. `settings.text_gate=false`(기본):
   잔글씨여도 생성, 검사는 로고 · 마크만(글자 앵커 · 읽은 글자 제외), 없던 글자 검사 · 글자 읽기 생략.
   결과 아래 "글자 · 라벨 · 인증 스티커를 가까이 찍은 사진" 요청 (`detail_requests`)
2. **구도가 중요** (대표가 거의 물건 하나) — 정답 구도에 필요한 사진이 없으면 요구.
   처음엔 각도 목록(`VIEW_NEEDS`)과 낱말 매칭으로 만들었다가 **틀렸다** — 사용자: "view 를 정해 놓지 말고 모델한테"
   (10-09 에 규칙 각도 대신 AI 사진 검토로 간 것과 같은 결정). → `detector.composition_check`: 판매자 사진 + 정답 사진을 보고
   `{ok, need(어느 방면 사진), why}`. eval `--view-check` 면 ok=false 일 때 **생성하지 않고 "구도 부족" 으로 기록**, 사용자가 나중에 평가.
   피드백에 "📷 원본에 이 구도 사진이 없음" 태그(`view_missing`) — 모델 탓이 아니라 사진 탓으로 따로 모아 검사를 고칠 근거로
3. **생성과 배경 교체는 별개** — 생성을 고르면 어떤 이유로도(잘림 · 겹침 · 내부 사진 · 분석 실패 · 검사 탈락) 배경 교체 · 원본으로
   돌리지 않는다. 1회 재생성 뒤엔 마지막 결과 + 탈락 기록. 배경 교체를 고르면 오리기가 실패해도 생성으로 넘어가지 않고 원본.
   eval `run_posts.py --mode generate`(기본) — "실패할 것 같아도 돌린다, 테스트일 뿐"
