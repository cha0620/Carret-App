## 1. FLUX.2 공식 프롬프트 안내 읽기 — 지금 프롬프트와 다른 점

계기: 10-08 코트 flash 1차에 원본에 없는 라벨 글자, 2차에 후드 모양 바뀜. 지금까지 프롬프트를 감으로 고쳐 왔고 공식 안내를 읽은 기록이 없었다.

읽은 곳: BFL 공식 FLUX.2 프롬프트 안내(docs.bfl.ai/guides/prompting_guide_flux2), fal flux-2 flash 개발자 안내, fal `flux-2/flash/edit` llms.txt.

| 공식 안내 | 지금 `CLEAN_PROMPT` | 판단 |
|---|---|---|
| **부정 프롬프트를 지원하지 않는다** ("FLUX.2 does not support negative prompts"). "no blur" 대신 "sharp focus" 처럼 원하는 모습을 쓴다 | "Do not add … no new labels, tags, logos, text …", "Do not repair …", 재시도 시 "drew marks …" | 가장 큰 차이. 금지어로 넣은 "label · text" 가 오히려 떠올리게 했을 수 있다 (1차 라벨 글자). 검증 안 됨 |
| **앞 단어가 더 중요하다**: 주 대상 → 동작 → 스타일 → 맥락 순 | 첫 문장이 배경 · 조명 | 물건 보존 문장을 앞으로 |
| 길이 30~80 단어가 보통 적당, 80+ 는 복잡한 장면용 | 약 190 단어 (재시도 문장 포함 시 더 김) | 줄일 여지 큼. flash 는 특히 |
| 여러 장 입력은 **각 이미지의 역할을 말해 준다**. 번호로 부르는 문법은 따로 문서에 없음 | "FIRST image … LAST image is only a LINE DRAWING" | 역할 설명은 이미 하고 있음. "image 1" 표기가 낫다는 근거는 없다 (내가 미리 짐작한 것 정정) |
| JSON 프롬프트도 똑같이 이해. 보존용 예시 필드 `"color_match": "exact"`, `"detail_preservation": "high"` | 자연어만 | 시도해 볼 만한 후보 |
| 상품 사진은 카메라 · 조명 설정을 구체적으로, 색은 hex 로 물체에 묶어서 | "soft even lighting, subtle shadow" | 색 hex 고정은 옷 색 바뀜에 쓸 수 있음 (나중) |

fal `flux-2/flash/edit` 설정 (llms.txt):
- `image_urls` 최대 4장 (넘으면 앞 4장만) — 코드 `MAX_IMAGES = 4` 와 일치
- 입력은 1MP 로 줄여서 씀. 값 $0.005/MP (입력 + 출력)
- `guidance_scale` 기본 2.5 (0~20). 사진 느낌은 2.0~2.5 권장 (생성 엔드포인트 기준 안내)
- `enable_prompt_expansion` 기본 false — 켜면 모델이 프롬프트를 늘린다. 보존이 중요한 우리는 꺼 둔다
- `steps` 는 edit 입력 목록에 없음 → 코드의 `GEN_STEPS = 8` 이 실제로 먹는지 확인 필요

## 3. qwen-image-3/edit 실험 (`qwen3-1009`)

사용자 허락: "일단 qwen해봐" — 코트 · 장난감 2건, 최대 4장. 조건: `--ref-text --ref-sketch --clean-prompt --model fal-ai/qwen-image-3/edit`.
코드 (기본 꺼짐, 모델 이름에 qwen-image 일 때만): `generator._model_args` 에 최대 3장 · `negative_prompt`(`QWEN_NEGATIVE`) ·
프롬프트 확장 끄기, `pipeline.QWEN_PROMPT` — "image 1 · image N" 번호로 역할, 금지 문장 없이 물건 보존을 맨 앞에.

| 물건 | 1차 | 2차 | 최종 |
|---|---|---|---|
| 코트 | **다른 코트** — 숄 같은 후드가 셔츠 깃으로, 원단도 리넨처럼, 목에 없던 태그 글자 | 1차와 같은 셔츠 깃 코트 + 태그 글자 | 배경 교체 (게이트 탈락) |
| 장난감 | 설명서 2권 → 상자 1개로 합침, 표지 그림 뭉개짐, **없던 사람 피규어 1개 추가** | **차량이 완전히 다른 차로**, 설명서에 우리 검사 표시 `[presence only]` 글자가 그려짐 | 배경 교체 (게이트 탈락) |

- 물건 보존은 flash 보다 확실히 나쁘다. 번호로 역할을 말해도 선 그림 · 정답 구도 쪽 모양(셔츠 깃 코트)을 물건으로 가져갔다 — 추정, 정답 원본 사진은 넣지 않았으니 선 그림에서 온 것
- 장당 5~6분 (flash 1분 안쪽). 가격은 fal 페이지에 안 나와 청구 내역으로 확인 필요
- **버그 (모델과 무관)**: 게이트 재시도 문장(`gate_note`)에 검사 목록 표시 `[presence only]` 가 그대로 들어가 생성 이미지에 글자로 그려졌다. `prompts/__init__.py` 검사 목록 줄 형식을 재시도 문장에도 쓰는 듯 — 재시도 프롬프트에서는 빼야 함
- 결론: qwen-image-3/edit 는 이 용도(물건 그대로 · 구도만 바꾸기)에 안 맞는다. flash 문장 실험(§2)으로 돌아간다

### 3-1. 최소 프롬프트 (`qwen3-min-1009`, 코트 1건)

사용자: "프롬프트를 최소화 — 나열된 거 다 빼고 코트라는 거 빼고". `--min-prompt` (`pipeline.MIN_PROMPT`): 메인 사진 + 선 그림만,
negative_prompt 없음, 재시도 문장도 안 붙임.

> Image 1 is the item. Image 2 is a line drawing that only shows the framing. Photograph the item from image 1 exactly as it is, standing upright, front view, centered, on a pure white studio background.
>
> (번역) image 1이 물건입니다. image 2는 구도만 보여 주는 선 그림입니다. image 1의 물건을 있는 그대로, 똑바로 세워, 정면에서, 가운데에, 순백 스튜디오 배경으로 찍어 주세요.

- **1차에 게이트 통과 → 생성 결과 그대로 채택** (136초). 숄 같은 후드 모양 · 앞 여밈 · 소매 탭 · 색이 원본대로, 없던 태그 글자도 없다
- 긴 프롬프트(§3)의 셔츠 깃 코트와 정반대 — 같은 모델 · 같은 입력에서 **문장만 줄였는데** 물건이 살아났다.
  목록("tags, logos, text, stain…")과 negative_prompt 의 단어들이 오히려 흔한 코트 · 태그를 끌어온 것으로 보인다 (10-08 "이름을 쓰면 흔한 모양으로" 와 같은 방향). 1건이라 운일 수 있음
- 아쉬운 점: 허리 옆 주머니 입구 선이 생김 (원본 정면에선 안 보임 — 다른 각도에 있는지 확인 필요)

### 3-4. 세트 JSON 자동 생성 + 개수 게이트 (`setauto-flash-1009`)

`--set-prompt`: 분석 objects(판매자가 고르면 고른 것만)로 `set_pieces` → `set_prompt` JSON, `count_gate` 켬. 손으로 쓴 §3-3 과 거의 같은 문장이 자동으로 나왔다 (booklet → "instruction manual").

- 1차: 설명서 2 · 본체 · 피규어 3 · 정답 배치 모두 좋음. **없던 글자 '2' 로 탈락** — 오른쪽 설명서 귀퉁이 표시로 보임 (§3-3 의 "1" 과 같은 종류의 오탐 의심)
- 2차: 개수 게이트 `{instruction manual 2, main piece 1, minifigure 3}` 일치 → **통과 · 생성 채택** (77초). 왼쪽 집게 날이 본체에서 떨어져 나온 것처럼 보임 (모양 변화 — 개수 게이트로는 못 잡음)
- 결론: 세트 경로가 자동으로 돌아간다. 남은 약점은 (1) 설명서 숫자 · 아이콘 오탐 (2) 부품이 본체에서 분리되는 모양 변화

### 3-5. 화면 — 발견된 물건 세 가지 선택 (사용자: "구성품 · 부가품 선택은 판매자가")

물건마다 [사진에 넣기] [부가품] [안 팔아요]. 사진에 넣기 = `sell` (생성 · 세트 JSON · 개수 게이트가 이것만 본다), 부가품 = `accessories` (같이 팔지만 사진에서 뺀다, 응답에 그대로). 기본값은 분석 role.
판매자가 고르면 정답 사진의 부가품 자동 처리(`shows_accessory`)는 끈다. State 에 `objects` 가 없어 그 처리가 그동안 한 번도 안 돌았던 것도 고침.

### 3-6. 앱 반영 (사용자 허락: 표 2 · 3, 7 은 "문서는 상세 사진칸", 모델 flash)

- 앱 `/api/transform` 이 `clean_prompt="set"` — 세트면 종류 · 개수 JSON + 개수 게이트, 아니면 `MIN_PROMPT`.
  배경은 고른 분위기(`get_preset` 의 `background`, 노트 포함). 남긴 기능 문장: 정답 구도 문장(선 그림과 같이), 정석 구도, "안 팔아요" 물건 빼기.
  뺀 것: SECONDHAND_LOCK · 글자 잠금 · 재시도 사유 (최소 프롬프트 원칙 — 재시도는 seed 가 달라 같은 문장이어도 다른 그림)
- 화면: 구성품 종류 · 번호(`[사진에 넣기][부가품][안 팔아요]`), 정답 구도 고르기(선 그림), 같은 물건 다른 사진 2장 같이(서버가 같은 묶음 · 같은 물건 · 상품 사진인지 확인), 근거 문서는 결과 아래 "상세 사진"
- 알려진 한계: 로그인이 없어 item_id · file_id 를 아는 사람은 그 묶음 사진을 쓸 수 있다 (원래 토큰 방식과 같음). 라우트가 items._load 를 직접 씀 (저장소 서비스로 옮길 것)

- "구성품 · 부가품 선택은 판매자가" → 화면에서 물건마다 고른다. 처음엔 3가지(사진에 넣기 · 부가품 · 안 팖), 마지막엔 **4가지(본품 · 구성품 · 부가품 · 안 팔아요)**,
  AI 추천(role)이 기본. 판매자가 고른 본품은 `TransformRequest.mains` → `set_pieces` 의 "main piece" · `apply_selection` 의 개수
- "박스, 설명서, 미니피규어 1, 2, 3 이런 걸 알려줘야지" → 같은 종류는 번호, 이름은 VLM `name_ko`. Langfuse 에 프롬프트가 없어 저장소 프롬프트가 그대로 쓰인다 —
  처음에 "Langfuse 에 올려야 보인다"고 한 건 틀렸다 (로그의 "not found … fallback" 을 보고 정정)
- "물건은 하나여도 구성품은 하나가 아니니까" · "보드게임이면 안에 든 걸 알려줘야지" → 분석 · 구성품 프롬프트에 **세트는 부품까지 쪼개기**, 안이 안 보이면
  `contents_hidden` 경고 ("펼쳐 찍은 사진을 넣어 주세요" — 지어내지 않는다)
- "3장밖에 못 넣으니 구성품은 3장 안에" → 생성 입력 = 기준 1 + 같이 넣기 2. 근거 문서(인증서 · 영수증)는 생성에 안 넣고 결과 아래 **상세 사진** 칸
- **게시글 구성품 목록** (`POST /api/components`, lite) — 기준 + 참고 사진을 같이 보고 `photo` 번호를 붙인 하나의 목록. 전체 분석과 **동시에** 부른다
  (분석 8~26초를 기다리지 않게). 판매자 번호가 같은 물건을 가리키도록 목록은 한 곳(`_components.json`)에만 두고, `load_analysis` 가 읽을 때 덮는다
- "원론 칸에 3개 다 담겨야 3개를 쓰는 줄 알지" → 원본 칸 = ★기준 + 참고 2장 + "대표사진에 담길 것" 목록
- **틀린 이름**: 입력 사진에 "★대표"라고 붙였다가 사용자: "인풋에 대표사진이 왜 있지?" — 대표사진은 결과물. 입력은 **기준 사진** · **참고 사진**으로 고쳤다
- "사진 속 물건 확인 파트 자체가 의미가 없다" → 지우고 **상품 이름 · 설명**만 남겼다 (§8 의 레이아웃)
- 사용자: "가급적 생성하고 싶어서 오리는 건 최후에" — 구성품을 오려 배치하는 안은 내려놓음 (메모리)

## 6. 세트 배치를 모델이 — 정답 사진 기준 (`layout_plan`)

- 규칙 배치("설명서 · 상자는 뒤, 나머지는 앞줄")는 넓은 판 · 높은 상자 · 작은 카드가 섞이면 못 맞춘다
- `detector.layout_plan(정답 원본 사진, 판매자 사진, 구성품)` → 한두 문장 (좌표 · 이름 · 금지 목록 없이), 세트 JSON 의 `layout` 자리에.
  **정답 원본 사진은 이 판단에만** — 생성 입력에는 넣지 않는다 (물건을 베낀다, 고정 규칙). 같은 정답 · 구성 · 참고 사진 수면 저장해 둔 문장 (`_layout_<hash>.json`)
- 정답 기본값은 "자동"이 아니라 **품목에 맞는 것** (사용자) — 물건 이름에 정답의 품목 낱말(`items`)이 있으면 그것 (보드게임 → `style_pack`)
- 아직 실제로 돌려 보지 않음 (유료 — 허락 대기)

## 7. 규칙 각도 → AI 사진 검토 (`photo_review`) · 시간 · 비용

**오해 두 번**: 사용자 "위아래 이런 게 애매하다"를 (1) 구도 부족 경고 따로, (2) 배치 이야기로 읽었다 — 실제로는 **사진 각도 라벨("위에서 본 사진", "각도 모름")**.
(2)로 만든 "배치 미리 보기 API" 는 되돌렸다.

- 묶음(`objects`) 프롬프트에서 각도(view) 질문을 뺐다. 가림 · 흐림 · 잘림은 그대로
- `POST /api/items/{id}/review` (lite) — 상품 사진(근거 제외, 최대 8) + 고른 정답 사진 → 사진마다 **보이는 것**("게임판 앞면", "코트 상반부"),
  **더 올리면 좋은 사진**(최대 4), **기준 사진 추천**, **같이 넣을 사진 추천**. 정답에는 `needs`(필요한 부위 · 면, `style_refs.json`)
- 규칙 `coverage` 의 빠진 면 · 각도 라벨 · 예시 구도(신발)는 화면 응답에서 비움 — 정답 구도 고르기로 통일
- 판매자가 직접 누른 기준 사진 · 직접 바꾼 같이 넣기는 AI 가 바꾸지 않는다. AI 가 같이 넣기를 비워 주면 "넣지 않음"이 아니라 자동으로 채운다 (한 장만 보이던 버그)

Langfuse 최근 기록 (10-01 이후, 사용량 한도로 일부만 — 직접 조회한 값):

| 호출 | 모델 | 1회 비용 | 시간(중앙) |
|---|---|---|---|
| objects (묶기) | lite (기록엔 3.8 섞임) | $0.003 | 3.4초 |
| components | lite | $0.002 | 2.1초 |
| photo_review | lite | $0.002 | 3.8초 (1건) |
| analyze | 3.8-flash | $0.005 | 5.6초 |
| 생성 (flash) | fal | 약 $0.01 | 14.7초 |

업로드 ~ 변환 전 물건 1개: $0.008 → 약 $0.012 (+5원 정도). 구성품 목록이 뜨는 시간은 분석(6~26초) 대신 구성품(약 2초) 뒤로.
