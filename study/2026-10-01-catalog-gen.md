## 4. 정리: 한 장으로 구도 바꾸기는 실패 — 여러 각도 업로드로 워크플로우 재설계

### 4-1. 판단 (사용자 결정)

catalog-gen · listing-clothes · listing-shoes 는 **실패로 본다**. 사진 한 장을 주고 생성 모델에게 구도를 바꾸게 하면,
모델이 원본에 없던 면을 상상해서 그려야 한다 — 가려졌던 깔창 로고(none_shoes1), 3/4 로 돌린 신발 옆면.
종류별 예시를 넣으면 다른 물건까지 그렸다(신발 뒤 재킷). 프롬프트 문장을 늘려서는 "구도를 크게 바꿔라"와
"아무것도 지어내지 마라"를 동시에 만족시키지 못한다.

참고 구도(신발 한 켤레 나란히 · 앞쪽 3/4)로 통일하는 문장도 만들었다가 뺐다 — 위에서 찍은 원본을 3/4 로 바꾸면
옆면을 지어내야 해서 같은 문제다.

### 4-2. 새 흐름

1. **여러 장 · 동영상 업로드** (`POST /api/items`, 더 올리기 `/api/items/{id}/files`)
   - 동영상은 `services/video.py` 가 VLM 없이 고른다: 고른 간격 후보 40장 → 흐린 것(선명도 중앙값의 0.35배 미만) 빼기 →
     마지막으로 고른 장면과 거의 같은 것(32×32 흑백 평균 차이 6 미만) 빼기 → 최대 8장. 90초 · 100MB 상한
2. **각도 분류 + 빈 면 체크** — `detector.classify_views`: 모든 사진을 VLM 1회, low 해상도(장당 268 토큰)로
   종류와 사진별 각도(정면 · 앞쪽 비스듬히 · 옆 · 뒤 · 위 · 밑창 · 안쪽 · 라벨 · 가까이) · 가림 · 흐림.
   필요한 면은 코드(`services/coverage.py` REQUIRED)가 종류별로 정한다 — 같은 물건에 매번 같은 안내가 나오게.
   가려졌거나 흐린 사진은 면을 채운 것으로 치지 않고 "다시 찍기"로 알려준다
3. **구도 고르기** — 사용자가 원하는 각도의 사진을 고르면 그 file_id 로 기존 `/api/transform`
4. **생성은 구도 유지 · 정리만** — `SECONDHAND_LOCK` 을 "이 사진의 카메라 각도 그대로, 가운데 · 화면 채우기 ·
   살짝 바로 세우기 · 구김 · 옷걸이 · 손 빼기". listing 에서 효과 있던 문장(다른 물건 추가 금지 · 자막 금지 · 질감 유지 ·
   가려졌던 곳 지어내기 금지)은 남김. listing 잠금은 `LEGACY_LOCKS` 로

비용: 각도 분류는 사진이 늘어도 장당 low 268 토큰. 생성은 고른 한 장만이라 사진 한 장일 때와 거의 같다.

## 5. 새 워크플로우 정리 — 단계 · 모델 · 비용 · 시간, 리뷰에서 고친 것

### 5-1. 흐름

```text
[1] 업로드          사진 여러 장 / 동영상 (+ "더 올리기")        POST /api/items · /api/items/{id}/files
     │  동영상 → 장면 고르기 (OpenCV, 서버 CPU)                 services/video.py
     ▼
[2] 각도 분류 + 빈 면   사진 전부 VLM 1회 (low)                  detector.classify_views
     │  → 종류 · 사진별 각도 · 가림 · 흐림
     │  → 코드가 종류별 필요한 면과 비교                         services/coverage.py
     │  → "이 면이 없어요" · "이 사진은 다시 찍기"  ──→ [1] 로 돌아가 더 올리기
     ▼
[3] 구도 고르기       원하는 각도의 사진 1장 (모델 없음)           프론트 renderItem / selectPhoto
     ▼
[4] 변환            고른 사진만 — 구도 그대로 정리               POST /api/transform (기존 그래프)
     analyze → (글자 있으면) 글자 읽기 → 생성 → 구도·자막 확인 → 보존 검사
       → 실패면 재생성 1회 → 그래도 실패면 배경 교체
     ▼ 응답 뒤: 성적표(judge) · 누끼 비교(DINO)
[5] 결과 · 성적표 · 피드백
```

사진이 한 장일 때보다 늘어나는 건 각도 분류(약 $0.001, 수 초)뿐 — 비용은 고른 한 장의 생성이 정한다.
VLM 이미지 비용은 장수에 정비례(해상도 등급으로 정해짐: low 268 / medium 542 / high 1,066 토큰)라
여러 장은 low 로 보고, 자세한 분석은 대표 사진 한 장에만 한다.

reviewer 가 23개, tester 가 5개 의심을 냈다. 고친 것:

### 5-4. 교훈

- 보이지 않는 면은 프롬프트로 지킬 수 없다 — 문제를 생성 단계가 아니라 **입력 단계**(무엇을 찍게 하나)에서 풀었다
- 필요한 면은 VLM 이 아니라 코드가 정한다 — VLM 은 "보이는 것"만 답하게 해야 같은 물건에 같은 안내가 나온다
- 저장 경로를 하나 바꾸면(normalize 를 거치게) 예전 경로가 기대던 것(브라우저의 EXIF 회전)이 조용히 사라진다

## 6. 신발 정석 구도 · 사진별 경로 · 글자 읽기를 analyze 에 합침

### 6-1. 신발 정석 구도 (`services/compositions.py`)

업로드 화면에 "고를 구도"가 없었다 — 내 사진만 보였다. 신발 정석 구도 5개(대표컷 앞쪽 비스듬히 · 옆모습 · 위에서 ·
뒤꿈치 · 밑창)를 카드로 띄운다. 구도마다 **그 구도를 만들 수 있는 사진 각도**를 적어 두고, 맞는 사진이 없으면 점선 카드 +
"이 각도로 찍어 올려 주세요". 고른 구도는 `/api/transform` 의 `composition` 으로 가서 생성 프롬프트에 틀(가운데 · 여백 · 수평)
문장만 붙는다 — 각도를 바꾸라는 말은 테스트로 막았다. 그림은 직접 그린 선 그림(SVG, 남의 상품 사진을 쓰지 않음).

### 6-2. 사진별 경로 (`eval/report.py` route_trace)

결과 필드로 "analyze(종류/하자/글자) → 글자 읽기 → 생성 ×n → 게이트 → 배경 교체[사유]"를 한 줄로 다시 짜서 보고서에
같은 경로 묶음 · 사진별 표로 넣었다. 노드 기록이 아니라 재구성이라 "생성 ×2"가 게이트 재시도인지 구도 반려인지는 모른다.

보인 것: 같은 사진이 회차마다 경로가 갈린다 (none_car2 하자 light/heavy, none_shoes1 r1 은 매번 게이트 실패 · r2 통과).
후퇴가 켜진 실행에서 none_shoes4 는 4번 중 4번 배경 교체.

### 6-3. 신발 실패 원인 → 글자 읽기를 analyze 에 합침

| 실패 | 원인 |
|---|---|
| none_shoes4 r1 · r2 | 글자 읽기 응답 끝에 엉뚱한 토큰(`缸`, `calendar`)이 붙어 JSON 이 깨짐 → `texts: []` 로 조용히 넘어감 → 글자 잠금 없이 생성 → 혀의 sacai 라벨이 뭉개짐 → 게이트 실패 ×2 |
| none_shoes1 r1 | 글자 잠금은 있었다(asics ×2). 첫 시도 혀 · 깔창 글자, 재시도엔 앞코 로고까지 바뀜 — 재시도가 더 나빴다. 실패한 생성 이미지는 배경 교체본으로 덮여 남지 않음 |

판단: 글자 읽기를 포기하지 않는다 — 비용은 변환 1건의 약 8%(VLM 의 21%)이고, 빼면 로고가 뭉개져 게이트에서 생성 비용을
버린다. 대신 **analyze 가 글자까지 읽는다** (`texts_analyze.md`, Langfuse `analyze_v2`):

- VLM 호출 1회 · 약 3초 · VLM 비용 약 1/5 절약
- 깨진 응답은 analyze 의 재시도 → `detect_failed` 로 드러남 (조용히 "글자 없음"이 되지 않음)
- 글자는 `text_level` 이 simple 일 때만 받는다. 응답에 texts 목록이 없으면(옛 프롬프트 · 저장된 옛 분석) 예전처럼 따로 읽는다
- 위험: 한 호출에 일을 더 시켜 마크 · 글자를 덜 꼼꼼히 볼 수 있다 — 짝 비교로 재야 함
