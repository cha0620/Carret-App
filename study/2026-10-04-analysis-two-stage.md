## 1. edge 층 정리 — 판단이 애매한 것만 층으로, 나머지는 태그 (커밋 전)

10-03 §4 에서 정한 방향(edge 는 층이 아니라 태그)을 수집 규칙 · 도구에 옮겼다.

- `eval/docs/COLLECT.md`
  - `edge` 층은 **판단이 애매한 것만** — 의도된 손상인지 하자인지 · 글자 · 그림이 곧 물건인지 · 팔 물건과 소품 · 구성품이 섞였는지.
    검색어: 데미지 청바지, 디스트레스 청바지, 포토카드, 엽서, 앨범 풀구성, 보드게임 (목표 7 / 3 그대로)
  - §2-1 **edge 태그 16개** — 어느 층 사진에든 여러 개. 묶음: judge(판단 애매) · cut(오리기 · 검출) · gen(생성에서 망가지기 쉬움) · privacy.
    유리컵 새것 = `none` 층 + `transparent`. 여러 개는 태그 대신 `item_count`
  - edge 층 사진엔 judge 태그가 하나 이상. 거꾸로 judge 태그가 붙었다고 edge 층은 아니다 (옷걸이에 걸린 옷 = `prop` + none 층).
    `ambiguous=y` 는 따로 — 라벨 다는 사람이 정답을 확신 못 할 때
  - 최소 5장은 **검색어로 노릴 수 있는 태그만** (transparent · glossy_material · packaging · pattern · 여러 개).
    층 목표를 채운 뒤 ⚠ 인 것만 보충 검색어로, **첫 사진에 노린 태그가 없어도 담는다**
  - 보충 사진은 `add --supplement` — **층 목표 밖 · 전부 dev**. 실패하기 쉬운 성격을 노려 모았으니 test 에 넣으면 통과율이 실제보다 낮게 나온다
- `eval/intake.py`: 라벨 CSV 에 `category`(필수) · `item_count`(빈칸 1) · `edge_tags`(`|` 구분) 열, `status` 에 태그 표, `--supplement`,
  test 동결 칸(`FROZEN`)에 category · item_count · edge_tags · ambiguous
- `eval/run.py`: `dataset_sha` 에 `item_count` — 여러 개면 경로가 바뀌니까. **이전 실행과는 해시가 다르다** (기준선을 아직 안 돌려서 지금 바꿈)

## 2. 카테고리 — 플랫폼은 고정 목록 + AI 추천, 임베딩으로 바꾸기 전에 재기

질문: 당근 같은 곳은 카테고리 태그를 미리 다 써 두나, AI 값을 받나.
→ 보통 **목록은 고정, AI 는 그중 하나를 추천**. 단서는 사진보다 제목이 큰 경우가 많고, 학습 정답은 판매자가 고른 카테고리(공짜 라벨).
당근 내부 구현은 확인 못 함 — 일반 구조.

Carret 도 같은 구조다: `coverage.CATEGORIES` 고정, `detector.classify_views` 가 VLM 값을 `norm_category` 로 거른다 (목록 밖은 other).
eval 의 `category` 는 앱 기능이 아니라 **이 추천이 맞았는지 재는 정답**이다.

"JEPA 같은 임베딩으로 분류할까" → 지금은 아니다:

- 종류는 VLM 호출 하나에서 같이 받는 필드라 빼도 호출이 그대로 — 아끼는 게 없다
- JEPA · DINO 는 글자와 연결이 안 돼 종류마다 라벨 단 예시가 수십 장 필요 (지금 29장, 신발 3장). 그래도 간다면 이미 있는 DINOv2 + 이웃 찾기, 라벨 없이는 CLIP · SigLIP
- **detector 의 종류 정확도를 잰 적이 없다** (eval 은 한 장 변환 경로만) — 29장 정답과 대 보는 게 먼저

## 3. DINO 로 라벨을 대신할 수 있나 — 다른 질문이다

- DINO 는 **두 장이 얼마나 닮았나**. "이 사진에 하자가 크다"는 한 장의 성격이라 DINO 에게 물을 수 없고, 학습시키려면 라벨이 먼저 있어야 한다
- 작은 변화도 못 가른다 — 채점(대부분 claude 1차)과 `item_dino` 를 대 봄 (생성 결과만, 대략):

| 채점 | 수 | item_dino 중앙 | 범위 |
|---|---|---|---|
| 물건이 바뀜 (모양 · 색 · 하자) | 27 | 0.918 | 0.81 ~ 0.987 |
| 그대로 | 39 | 0.958 | 0.327 ~ 0.994 |

- 라벨은 두 군데 다른 것: **앱 분석 값**(AI 가 매김, 경로 결정)과 **eval 라벨**(사람이 미리 단 정답 — AI 값 채점 · 분모 · 수집 층)

## 4. wear_level 을 뺀다 — VLM 은 봤는데 질문이 막았다

사용자: 너무 애매하다, 디자인이랑 구별이 안 된다.

처음 제안은 **판매자가 상태를 고르게** 하기(번개장터 "상품 상태"처럼) — 사용자가 기각: 모델이 스스로 판단해 생성해야지 판매자에게 묻는 건 의미가 없다.

다시 보니 애매한 건 질문이었다. edge_clothes2 실제 분석:

| 실행 | `considered` | `wear_level` |
|---|---|---|
| 10-01 listing-clothes | hole · printed text · stain · fading · tear | none |
| 10-01 lock-trim | tear · hole · fading · stain · printed text | none |
| 10-03 added-text | printed text · graphic print · distressing · tear · stain · fading | none |

- VLM 은 세 번 다 구멍 · 찢김 · 디스트레스를 **봤다**
- `rules_analyze.md` 가 막았다: wear_level 은 "Judge only real damage, not intentional distressing or design", marks 는 "Do NOT list damage, wear …".
  그래서 구멍이 들어갈 곳이 `considered`(검증 힌트)뿐이었고, 경로는 그걸 안 본다
- 하자를 marks 에서 뺀 이유(09-27)는 "목록으로 넘겨 지켜라 하면 생성 모델이 하자를 지어낸다" — **생성 프롬프트에 넣었을 때**의 문제다. 경로 · 게이트에서만 쓰면 생기지 않는다
- 경로에 필요한 건 "하자냐 디자인이냐"가 아니라 **"생성 모델이 똑같이 다시 그리기 어려운 흔적이 표면에 넓게 있나"**.
  디자인 찢김이든 하자든 둘 다 원본 그대로여야 하고, 생성은 둘 다 메운다 (edge_clothes2 8/8 · 굴삭기 녹이 같은 실패)
- 역할 나누기: VLM 은 **보이는 것**(넓은 흔적이 있다), 우리 규칙은 **실험으로 안 것**(그런 사진은 생성하지 않는다). "우리 생성 모델이 구멍을 메운다"는 사진에 안 보인다

결정:

- `wear_level`(none · light · heavy, 디자인 제외) → **넓은 흔적 있음 / 없음** (구멍 · 찢김 · 녹 · 얼룩 · 디스트레스 · 워싱을 구분하지 않음). 이름은 미정 (`surface_marks` 안)
- 이 값은 경로 · 게이트에서만, **생성 프롬프트에는 넣지 않는다**
- 작은 흔적이 지워지는 건 생성 전엔 모른다 → 생성 뒤 "사라진 것" 게이트 (남은 일과 같은 작업)
- eval 라벨도 같은 질문으로 (있음 / 없음), 층 light · heavy 를 합친다. `intended_damage` 태그는 남김 (경로와 무관, 디자인 손상 사진의 실패율 보기용)

## 5. 분석을 두 단계로 (설계 초안, 코드 안 바꿈)

### 지금

- 업로드(여러 장): `classify_views` 1회 — `category` · `item` 하나씩 + 사진마다 `view` · `occluded` · `blurry` · `item_visible`. **모든 사진이 한 물건이라고 가정**
- 변환(사진마다): `analyze` 1회 — 12개 필드

| 무엇을 위해 | 필드 |
|---|---|
| 무엇이 찍혔나 | item · item_count · item_box · objects · considered |
| 어느 경로 | photo_type · wear_level · text_level · item_cut_off · watermark(안 씀) |
| 무엇을 지킬까 | anchors · item_texts |

겹치는 곳: objects 에서 고르면 item · count · box 가 나온다 / anchors 와 item_texts 는 둘 다 물건 위 글자 /
photo_type(document · inside_view)과 view(label · detail)는 둘 다 "어떤 샷이냐"인데 다른 호출에서 따로 받는다.

### 여러 장으로 들어오는 경우

| 경우 | 예 |
|---|---|
| A. 한 물건 여러 각도 | 신발 앞 · 옆 · 뒤 · 밑창 |
| B. 한 물건 + 설명 사진 | 택 · 사이즈 라벨, 하자 클로즈업, 보증서 · 영수증, 구성품 · 상자 |
| C. 여러 물건 | 사진마다 다른 물건, 한 장에 일괄 |
| D. 섞임 | 가방 3장 + 지갑 2장 |

### 바뀐 뒤

```text
업로드 ─▶ ① 묶음 분석 (모든 사진 · VLM 1회 · 낮은 해상도)
            groups: [{이름, category, 판매 여부, 사진 번호들}]
            사진마다 shot + occluded · blurry
         ─▶ 묶음 확인 화면 (AI 기본값, 사용자가 옮김 — 팔 물건 고르기와 같은 방식)
         ─▶ 묶음마다: 빠진 각도 안내 (coverage) · 대표컷 구도 후보 (compositions)

변환 ──▶ shot 이 경로를 먼저 정한다
            document · inside            → 원본 그대로 / 배경만 (지금과 같음)
            detail · label               → 원본 거의 그대로 (미정)
            전체가 보이는 각도            → ② 사진 분석
         ─▶ ② 사진 분석 (처리할 사진만 · VLM 1회)
            objects · texts · 넓은 흔적 · text_level · cut_off
         ─▶ 넓은 흔적 / 잔글씨 / 잘림 / 여러 개 → 배경 교체 (원본 픽셀)
            그 밖                                → 생성
         ─▶ 생성 뒤 비교 게이트 (원본 + 생성본 · VLM 1회): 생긴 것 + 사라진 것 · 개수
            떨어지면 배경 교체
```

- `shot` = 지금의 `view` + `photo_type` + `item_visible` 을 하나로: 전체가 보이면 각도(`front` · `front_34` · `side` · `back` · `rear_34` · `top` · `bottom`),
  아니면 `detail` · `label` · `document` · `inside` · `accessory`
- 사진 분석 12개 → 5개:

| 지금 | 바뀐 뒤 |
|---|---|
| item · item_count · item_box | objects 에서 고른 물건으로 계산 |
| considered | 없앰 (objects · texts 로) |
| anchors · item_texts | texts 하나 (글자 + 위치) |
| photo_type | ① 의 shot |
| wear_level | 넓은 흔적 있음 / 없음 (§4) |
| watermark | 없앰 |
| text_level · item_cut_off | 그대로 |

- 호출 수: 업로드 1회(지금 classify_views 자리) + 사진마다 1회(지금 analyze 자리) + 생성 뒤 비교 1회 — 어제 만든 없던 글자 검사에 "사라진 것 · 개수"를 합치면 늘지 않는다

### 정할 것

- `shot` 값 목록 확정 · `detail` · `label` 사진을 어떻게 처리할지
- 같은 물건 두 개 vs 한 물건 두 각도 — 묶음 확인 화면을 둘지 (AI 도 헷갈린다)
- 한 장만 올려도 ① 을 돌릴지 (안 돌리면 shot 을 ② 에서 받아야 함)
- 순서: **기준선 → 분석 변경 → 같은 사진으로 비교**. 지금 바꾸면 비교할 기준이 없다
- eval: 여러 장을 평가하려면 **게시글 단위**로 모아야 한다 (지금 규칙은 첫 사진 한 장). 게시글 사진 전부 + 첫 사진은 한 장 세트로도 — 모으기 전에 정한다

- 배치: 실제 크기 비율 · "상자 위에 얹기" 같은 배치 없음
- 묶기 품질 측정 — 게시글 단위로 모은 뒤 묶음 · 역할 라벨

## 13. 사진마다 처리 나누기 · 저장 구조 (제안)

- **VLM 은 보이는 것만, 처리는 코드 규칙이** — 각도가 흔들리는 걸 봤으니 결론을 VLM 에 맡기지 않는다.
  사진마다 `treatment`: 대표컷(hero) · 배경만(clean) · 원본(keep: 택 · 하자 · 구성품 · 근거) · 가림(mask) · 확인(ask)
- `accessory` 각도 (상자 · 구성품 샷) — 맥북 상자 사진은 "같이 간다"를 보여 주는 사진이라 배경을 바꾸면 정보가 사라진다
- **hero 는 사용자가 고르지 않는다** — 사용자는 예시 구도를 고르고, 그 구도에 맞는 사진이 대표 사진 (`compositions.options` · `best_photo` 가 이미 그렇게 한다). 처음에 "사진을 고른다"처럼 설명해 헷갈리게 했다
- 저장: 묶음 = `items/<item_id>.json` 하나 (DB 아님). 제안 — AI 원래 답을 `ai` 로 남기기 (판매자 수정 = 정답 라벨), 처리 방식은 사용자가 바꾼 것만, 고른 구도 저장, 구성품 칸

## 14. 각도만으로는 모자라다 — 노트북 상태 (open · closed)

문제: 펼친 노트북 정면 ≠ 닫은 노트북 정면. 맥북 상판(`top`)을 찍었는데 "뒷면 없어요"가 나왔다.

선택지: (가) 종류마다 각도 목록을 따로 / (나) 공통 각도 + 물건별 상태 몇 개 → **(나)**. 종류 판정이 틀려도 각도는 살고, 판매자에게 보이는 "상판 · 하판"은 코드가 조합으로 만든다.
사용자 결정: 물건별로 상태를 손으로 적는다, **노트북만 먼저**.

- 시험 (상태를 넣은 프롬프트, VLM 5회): 예시 `front_34` + 화면 켬, macbook1 `front` + 펼침, macbook2 `top` + 닫음 — 순서를 섞어도 4번 모두 같음
- 구현 (커밋 전):
  - `coverage.SUBTYPES = {"laptop": "electronics"}`, `STATES` (open · closed), `REQUIRED_SUBTYPE` — 펼친 앞면 · 상판 · 하판 · 옆면 단자를 (각도, 상태) 조합으로
  - `compositions.SUBTYPE_COMPOSITIONS` — 펼쳐서 비스듬히(`front_34`+open) · 펼쳐서 정면 · 닫은 상판, 선 그림 SVG 3개
  - 물건 `subtype` (VLM, 사용자가 종류를 바꾸면 버림), 사진 `state` (그 물건의 subtype 값만 — `_fix_states`), 응답 `state_label`, 화면 태그에 "· 펼침"
  - `objects.md` 에 subtype · state
- 실제 VLM 으로 맥북 6장: subtype laptop, 펼침 · 닫음 맞음. "펼쳐서 비스듬히"는 불가 + "펼침 상태로 앞쪽 비스듬히 사진이 없어요" 안내, 정면 · 상판 가능
- 빠진 면에 상판이 나옴 — 규칙은 맞다(top+closed 하나면 채워짐). macbook2 가 가림 · 흐림으로 잡혔을 가능성 (충전기가 위에 있다), 출력하지 않아 미확인
- 단위 테스트는 사용자가 바꿀 예정이라 기대값 두 곳(`state` · `subtype` 칸)만 맞췄다

## 15. 빈 곳 판정 — 네 방법 검토

"가진 사진들로 그 구도를 빈 곳 없이 만들 수 있나"를 어떻게 판정할까. 사용자 제안: 작은 모델을 학습해 판정 (생성은 큰 모델).
라벨(`view` 같은 중간 라벨)을 거치지 말고 사진만 보고 — 사용자 지적이 맞다, 각도 단어로 줄이면 가림 · 일부만 찍힘이 사라진다.
"어디가 비었는지" 설명도 필요하다 (O/X 만이면 판매자가 뭘 찍을지 모른다).

방법마다 Claude 하나씩 단점만 검토시켰다:

| 방법 | 가장 큰 단점 | 판단 |
|---|---|---|
| DINO 패치 맞추기 (라벨 없음) | 찍힌 화면도 "빔"(배경화면 달라 0.3~0.4), **좌우를 못 가림** (뒤집은 예시 0.90) — CPU 로 직접 잼, 장당 0.3초 | 다른 물건 거르는 보조 신호만 |
| 사람 O/X + 작은 머리 | 사람의 O/X 를 확인할 정답이 없다, 기준이 흔들림, 수백 개로는 암기 | 기준을 세운 뒤 100~200 개 기준선만 |
| 3D 영상 데이터 (CO3D 등) | 비상업 라이선스 가능성(확인 필요), 신발 · 옷 없음, 예시가 다른 물건이라 입력 모양이 다름 | 연구 검증용만 |
| VLM 에 직접 묻기 | 같이 넣은 사진에 따라 흔들림, "다 찍혔다"로 치우칠 위험 | 판정을 맡기기엔 불안 |

- 쓸 만한 정답 만드는 법: **사진 한 장 빼기** — 게시글 사진 하나를 목표로 두고 남은 사진으로 맞히게. 빼 둔 사진이 진짜 정답
- 처음에 DINO 를 "지금 바로 해 볼 만하다"고 추천했다 — 검토에서 좌우 문제로 핵심 기능이 안 된다고 나왔다

- 사용자 결정: 자판 글자는 어쩔 수 없으니 무시, **노트북은 되는 것으로 본다**

④ 프롬프트 (한국어): 이미지 1 · 2 의 노트북(같은 물건, 펼침 · 닫은 상판)으로 깔끔한 중고 판매 사진을. 이미지 3 은 카메라 각도와 배치를 보여 주는 선 그림일 뿐 — 앞쪽 왼편 약간 위에서 비스듬히. 그 각도와 배치를 따르고 순백 배경 가운데, 부드러운 그림자. 색 · 몸체 · 스피커 구멍 · 노치 · 자판 · 화면 내용은 오직 이미지 1 · 2 에서. 글자 · 로고를 더하지 마라.

### 19-1. Jev 에서 가져온 생각

Jev(TypeSafe AI)는 글을 쓰지 않는 판단 모델이다 — 고르기 · 점수 · 예/아니오를 **보정된 확률**로 돌려주고,
경로는 코드가 그 확률로 정한다. 우리 VLM 호출 대부분(구도 검사 · 마크 보존 · 없던 글자)이 이런 판단인데,
지금은 큰 생성형 모델에 JSON 을 쓰게 하고 확신도는 받지 않는다.
